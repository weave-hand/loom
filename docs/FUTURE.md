- [ ] **Run-grouped lifecycle stitching** `{#fut-lineage-stitching area:lineage status:deferred from:2026-06-05-control-plane-lineage-design pr:- spec:-}`
  The graph is per-event co-membership. OpenLineage allows a run to split inputs on START and outputs on COMPLETE across events sharing a `run_id`; stitching those is deferred (loom's emitters emit one terminal event).
- [ ] **OpenLineage payload validation** `{#fut-openlineage-validation area:lineage status:deferred from:2026-06-05-control-plane-lineage-design pr:- spec:-}`
  `payload` is stored opaquely as `jsonb`; a validating/parsing layer that derives the typed envelope from the payload is future work.
- [ ] **Hydrate only kept rows in paginated `events_for`** `{#fut-lineage-events-page-hydration area:lineage status:deferred from:2026-06-30-lineage-read-maturation-design pr:- spec:-}`
  Postgres `events_for` fetches `limit+1` rows (the `+1` detects a next page) and hydrates every event's inputs/outputs via two per-row `event_datasets` sub-queries **before** `Page::from_keyset` truncates the probe row away — so each page pays one discarded pair of round-trips. Correctness is fine (the probe row is only used to detect `next`) and the cost is bounded by the page size and off the hot path; the fix is to cut the keyset on the bare `event_id`s first, then hydrate only the survivors. Surfaced by the `#road-lineage-read-maturation` whole-branch review.
- [ ] **Lineage DatasetRef validation** `{#fut-lineage-datasetref-validation area:lineage status:deferred from:2026-06-21-existence-validation-design pr:- spec:-}`
  Carved out of `#iss-existence-validation`: validate the `DatasetRef`s a `LineageEvent` references on `emit`. Needs an internal-vs-external namespace convention first — a `DatasetRef` is deliberately opaque and may name an external dataset, so validating naively would reject legitimate external lineage. Relates to `#fut-dataset-naming-bridge`.
- [ ] **Storage-derived canonical lineage emit** `{#fut-storage-derived-lineage-emit area:lineage status:deferred from:2026-07-01-dataset-naming-bridge-design pr:- spec:-}`
  `#road-dataset-naming-bridge` added the deployment-aware `LineageNaming` bridge but kept loom emitting the **logical** `"loom"`/`"loom:type"` `DatasetRef` form internally (zero control-plane change); the storage-derived (`s3://<bucket>` / `file://<root>`) form is offered only at the external boundary. Switching loom's *canonical emitted* output ref to the storage-derived form — for full OpenLineage conformance in the stored graph — would thread `ObjectStoreConfig` into the control-plane emitters (`iceberg_flush.rs` et al.) and carry a data-migration tail. Deferred as non-breaking: the bridge's dual-recognition `resolve` already accepts both forms, so this is a later, independent decision. See the design's Open questions.
- [ ] **Batch/CTE-pushdown of the governed lineage closure** `{#fut-lineage-filter-batch-resolve area:lineage status:deferred from:2026-07-01-lineage-acl-filtering-design pr:- spec:-}`
  `#road-lineage-acl-filtering`'s `LineageVisibility` filter walks the closure one hop at a time, issuing one control-plane one-hop read **per frontier node per hop** (`K` calls/hop) plus one `Acl::check` per discovered node. Bounded by `depth` + `LINEAGE_FILTER_SCAN_CAP` and cheap for metadata graphs, but a wide closure is chatty. Future optimization: a **batch one-hop read** (`upstream_of(&[DatasetRef])`) or a **single recursive CTE that takes a readable-set predicate** — the latter needs the naming bridge to expose a *batch* resolver so query-api can pre-compute the readable set and hand the CTE a `WHERE (namespace,name) IN (…)` filter, keeping the ACL decision in the service layer. Also carries the design's **external-pass-through** threat-model question: external nodes are treated as readable and so *pass* traversal (cut) — revisit whether an external node bridging two internal subgraphs should *stop* traversal (visible but not expanded) under an adversarial model. Deferred until the chatty path is shown to matter.

## catalog

- [ ] **Incremental (append-delta) compaction output** `{#fut-compaction-incremental area:catalog status:deferred from:2026-06-22-engine-wire-compaction-flight-design pr:- spec:-}`
  The remaining half of `#fut-compaction-job`. `#road-compaction-job` shipped full-rewrite of the small-file set (every small file re-read and coalesced each run). Watermark-tracked incremental output would compact only files added since the last compaction watermark, avoiding O(table) rework on each run. Needs a per-table compaction watermark in the catalog and append-delta selection in the worker. Compacted files get fresh row-ids — revisit if/when row-level deletes land.

- [ ] **Per-table compaction-trigger override** `{#fut-compact-trigger-pertable-override area:catalog status:deferred from:2026-06-22-engine-wire-compaction-flight-design pr:- spec:-}`
  Deferred out of `#road-compaction-auto-trigger` (shipped, PR #419): the event-driven trigger's file-count threshold N is a single global env knob (`LOOM_COMPACT_TRIGGER_FILES`), unlike the byte-flush trigger which carries a per-table `iceberg_mirror.inline_trigger.threshold` override column. The compact trigger is stateless (its input — live small-file count — is already materialized in `iceberg_mirror.data_file`), so an override needs no migration coupling and was deliberately left to v2. Add a per-table override column/knob only if a real workload needs table-specific tuning.

- [ ] **Small-file compaction for stream / CDC / changelog tables** `{#fut-stream-smallfile-compaction area:catalog status:deferred from:2026-06-22-engine-wire-compaction-flight-design pr:- spec:-}`
  Deferred out of `#road-compaction-auto-trigger` (shipped, PR #419): the auto-trigger's eligibility guards skip declared stream tables, changelog tables, and shadow-flagged tables, because CDC/log files carry offset framing whose physical rewrite under `compact_table` is unproven and compacting under live inline deltas could resurrect tombstoned rows. A stream small-file story (offset-framing-aware coalescing) is a follow-on; CDC current-state folding is `consolidate_stream`'s job with its own trigger, and the COW-delta fold is `#road-cow-compaction-consolidation` (shipped). The operator endpoint now routes through the same guards (`#iss-compact-endpoint-unguarded`, closed by #434), so this deferral is the only remaining route by which a stream table could be compacted.

- [ ] **View-over-view (nested catalog views)** `{#fut-view-nesting area:catalog status:deferred from:2026-07-13-catalog-views-design pr:- spec:-}`
  `#road-catalog-views` (shipped, PR #438) deliberately restricts `ViewDef.base` to a **physical** table: `define_view` rejects a base that is itself a view (only a live `iceberg_mirror.table` row qualifies), and `validate_view_shape`/`fold_view` assume one flat `SELECT <columns> FROM base WHERE <predicate>` expansion. Letting a view's base name another view — composing predicates/projections transitively — needs recursive resolution on every read path that expands a view (`register_catalog_views`, the governed `execute_governed_sql_stream` loop, and the postgres adapter's `fetch_view`-based catalog delegation) plus a cycle guard, mirroring the ontology link/derived-property define-time cycle checks elsewhere in the tree. Deferred until a consumer needs a view defined over another view rather than always re-deriving from the physical base.

- [ ] **Arbitrary-SQL (join/aggregate) read-only views** `{#fut-view-sql-derived area:catalog status:deferred from:2026-07-13-catalog-views-design pr:- spec:-}`
  `#road-catalog-views` (shipped, PR #438) ships a view as base + optional `RowFilter` predicate + optional column projection — a row/column subset of exactly one physical table, expanded by `fold_view` as `SELECT <columns> FROM base WHERE <predicate>`. A richer view whose definition is an arbitrary read-only SQL query (a join across tables, an aggregate/GROUP BY) is a separately-shaped, larger primitive: it would need the view's definition to carry a governed query plan rather than a `(base, predicate, columns)` triple, and its expansion would likely ride the governed-SQL substrate (`execute_governed_sql_stream`/`GovernedTableProvider`) rather than `fold_view`'s flat `DataFrame` fold. Deferred until a consumer needs more than a row/column subset of one table.

- [ ] **Predicate-pushdown statistics for view scans** `{#fut-view-pushdown-stats area:catalog status:deferred from:2026-07-13-catalog-views-design pr:- spec:-}`
  `register_catalog_views`/`fold_view` (and the governed `execute_governed_sql_stream` view-registration loop) expand a view as an ordinary DataFusion logical `DataFrame` fold over the base's already-built provider — the view's own predicate becomes a plain filter evaluated above the base scan, not a predicate pushed into the base `IcebergMirrorTableProvider`'s `PruningPredicate` file-skipping the way ACL row filters are threaded through `GovernedTableProvider::scan`. A view read therefore never file-prunes on its own row-subset predicate. Pairs with the pre-existing `[[fut-governed-scan-pushdown]]` (which leaves the same optimization on the table for the governed-catalog primitive generally); deferred until view-scan latency is shown to matter on a real workload.

- [ ] **`define_view`-time rejection of a projection that excludes its own predicate column** `{#fut-view-predicate-projection-guard area:catalog status:deferred from:2026-07-13-catalog-views-design pr:- spec:-}`
  `validate_view_shape` only checks that a view's predicate column exists in the **base** schema, independent of the view's own `columns` projection — a view may legally declare a predicate over a column its projection then excludes. On the write path (`resolve_write_base`/`view_row_admits` in query-api's `action.rs`), the row `view_row_admits` gates against is built from the bound ontology type's **declared properties**; if that type exposes only the view's projected columns as properties, the predicate column is simply absent from the row map, `write_filter::eval` reads it as UNKNOWN, and the three-valued fail-closed semantics deny **every** write through the view — not a misconfiguration surfaced at `define_view` time, but a silent all-writes-forbidden trap discovered only when a caller tries to write. Reads are unaffected (`fold_view`'s `SELECT`/`WHERE` reads the predicate column straight off the base regardless of projection). A kinder fix rejects this shape at `define_view`: require the predicate's referenced columns to be a subset of the projection (or forbid the combination outright) rather than accepting a definition that write requests can never satisfy. Surfaced during `#road-catalog-views`'s review.

## ontology

- [ ] **Fine-grained (subject-attribute) access control — A7** `{#fut-fgac-subject-attribute area:acl status:deferred from:grimoire-kg-agenda pr:- spec:-}`
  Extend the literal-only `RowFilter` (`control-plane/core/src/acl.rs`) with **subject-attribute references** (an operand resolving to the caller's identity/attributes) and an **entitlement-join / `Exists` leaf** (row visible iff a matching entitlement row exists for the subject), for per-subject row access — multi-tenant RLS and large/dynamic subject populations. ACL is P4, literal-only today; the governed-SQL path (`#road-external-sql-governed-catalog`) enforces per-type literal filters only. **Superseded for the Grimoire consumer** (see `docs/grimoire-kg-agenda.md`): its fixed ~6-profile visibility is served instead by **dataset-partition-per-character + coarse per-dataset `Read` grants + hot-tier merge**, so no fine-grained ACL is needed there. Kept deferred as a **general** loom capability for consumers with large/dynamic subject sets. Design exploration recorded: a per-row **bitmask** filter (small fixed subject sets; needs a bitwise operator + subject→bit registry; time-travel-exact) and an **entitlement table + IN-list resolution** (avoids the DataFusion↔Postgres cross-source join by inlining) were both considered before the dataset-partition model made them unnecessary for Grimoire. **Catalog views** (`#road-catalog-views`, shipped, PR #438) now cover the **nameable, static-subset** half of this problem: an operator can carve a fixed `RowFilter`-defined slice of one physical dataset into its own `(schema, name)`-addressable, independently ACL-grantable view, without row duplication — a named, admin-declared subset, not a per-caller dynamic one. What remains genuinely deferred is **per-subject dynamic** filtering — a row-visibility rule keyed on the *calling* subject's own identity/attributes (a literal `RowFilter` predicate, and a view's predicate, can only be as dynamic as an admin is willing to pre-declare a view per subject/cohort) — the subject-attribute-reference and entitlement-join mechanisms above remain the residue for large or dynamic subject populations a fixed set of views cannot practically enumerate.

- [ ] **File-granular copy-on-write** `{#fut-cow-file-granular area:ontology status:deferred from:2026-06-27-update-delete-actions-design pr:- spec:-}`

- [ ] **Arrow-native COW read leg (lifts the vector guard)** `{#fut-cow-arrow-native area:ontology status:deferred from:2026-06-27-update-delete-actions-design pr:- spec:-}`
  `#road-update-delete-actions` rejects update/delete on vector-bearing types (`ensure_cow_supported`, `query-api/src/action.rs:427`) because the current COW read leg deserializes rows through `SqlValue` (which has no vector variant). Replacing that leg with a native Arrow batch read (read files as `RecordBatch`, apply the mutation per-batch, write back) would lift the guard and allow update/delete on any type including `vector(N)`. Depends on the file-read infrastructure from `#road-engine-wire-flight`. The rebuild-on-replace prerequisite is already in place: the overwrite/truncate commits enqueue a deduped `build_vector_index` job per declared index via the `rebuild_jobs_for` helper shared with `iceberg_flush::flush_table` (the fixed `#iss-overwrite-vector-index-staleness`), so lifting the guard needs no extra index plumbing — just verify the enqueue fires for the newly-reachable vector-indexed UPDATE/DELETE in the acceptance tests.

- [ ] **Uniqueness constraint (cross-row)** `{#fut-model-constraint-uniqueness area:ontology status:deferred from:2026-06-30-model-constraints-design pr:- spec:-}`
  `#road-model-constraints` enforces only **per-row** value rules. A non-identity **uniqueness** constraint (a column unique across all rows) needs a cross-row existence check at write — race-prone and index-backed, a different mechanism from per-row validation (closer to `identity`'s primary-key handling). Deferred until a non-PK uniqueness need surfaces; likely rides on the same indexing work that backs identity. A **Bloom-filter index blob** ([[fut-bloom-filter-index-blob]]) could later accelerate the common (value-is-new) path of this check.
- [ ] **Bloom-filter index blob (uniqueness acceleration)** `{#fut-bloom-filter-index-blob area:ontology status:deferred from:bloom-index-brainstorm pr:- spec:-}`
  Generalize loom's Puffin sidecar — today a single `loom-vector-index-v1` blob holding a `FlatIndex`, tracked by a `(table, column, index_name, covered_snapshot) → puffin_path` mirror row (`control-plane/postgres/src/puffin.rs`, `vector_index.rs`) — to a **second index-blob kind**: a serialized **Bloom filter** (`loom-bloom-filter-v1`) over a column's values, built at a covered snapshot and loaded by the engine. Its motivating use is **accelerating** the cross-row [[fut-model-constraint-uniqueness]] check. **Crucial framing — a Bloom filter *accelerates* uniqueness, it cannot *enforce* it:** false positives but no false negatives mean the only definitive answer is "definitely **not** present", so it is a **negative cache** — "not in filter" ⇒ value is new ⇒ skip the exact check (the common fast path); "maybe" ⇒ fall back to an exact lookup. Three loom-specific wrinkles: it is **snapshot-cold** like the vector index (uniqueness = not-in-cold-filter **and** not-in-hot-inline-delta, the same hot/cold merge), it does **not** provide the concurrency guarantee (two concurrent inserts of the same new value both pass — a commit-time CAS/exact check is still required), and plain Bloom filters **can't delete** so churn accrues false positives and needs periodic rebuild (mirroring `#road-vector-index-auto-rebuild`). Therefore **sequenced strictly after** [[fut-model-constraint-uniqueness]] (the exact mechanism it optimizes must exist first) — building the accelerator before the capability is backwards. Generalizing the vector-shaped `vector_index` mirror to carry a non-vector index kind is part of the work. (Distinct from **Parquet-native** column Bloom filters — a DataFusion write-config knob for equality *scan pruning*, `WHERE col = x` — which serve read pruning, not app-level uniqueness, and are the idiomatic lever for that separate goal.) Surfaced in the 2026-06-30 blob/index brainstorm.
- [ ] **Retroactive constraint validation / backfill** `{#fut-model-constraint-backfill area:ontology status:deferred from:2026-06-30-model-constraints-design pr:- spec:-}`

- [ ] **Richer multi-step action control flow (DAG / conditional / fan-out / loops)** `{#fut-action-step-control-flow area:ontology status:deferred from:2026-07-01-action-multi-object-design pr:- spec:-}`

- [ ] **Cross-step references inside expressions (`@bind.prop` in arithmetic)** `{#fut-action-cross-step-expr-refs area:ontology status:deferred from:2026-07-01-action-multi-object-design pr:- spec:-}`

- [ ] **MV — backfill / replay control** `{#fut-mv-backfill-replay area:transform status:deferred from:2026-07-09-stream-continuous-design pr:- spec:-}`
  A micro-batch MV starts at its source's earliest surviving offset (bootstrapped at registration — [[fut-mv-start-at-policy]]) and resumes from the committed watermark (`stream.mv_watermark`); rebuild = a new output table. A watermark-reset API / `from`-offset registration (replay a window, re-materialize in place) is deferred.
- [ ] **Per-def MV start policy (`start_at: Earliest | Latest | RequireComplete`)** `{#fut-mv-start-at-policy area:transform status:deferred from:2026-07-14-mv-register-source-floor-design pr:- spec:-}`
  `define_transform` bootstraps a new micro-batch MV to its source's **earliest surviving** offsets — the policy is fixed in code (`crate::mv_bootstrap`). Two other policies are coherent and were deliberately not built: **latest** (`stream.bucket_offset.next` — exact, per-bucket, already stored, needs no scan; Kafka's `auto.offset.reset=latest`, and arguably what an operator adding an MV to a long-running stream actually wants) and **require-complete** (refuse the registration outright if the source has been truncated past 0 — an explicit opt-in rather than the time-bomb default, since under any real retention policy every stream table eventually loses its prefix). Both fit a `#[serde(default)] start_at` field on `TransformBody::MicroBatch`/`MicroBatchJoin` (backward-compatible: bodies are JSONB). Deferred because it is a product decision, not a correctness one — the correctness half (never mis-read, never wedge, never over-hold) is closed by `earliest`.
- [ ] **MV — Parquet spill for oversized outputs** `{#fut-mv-parquet-spill area:transform status:deferred from:2026-07-09-stream-continuous-design pr:- spec:-}`
  Micro-batch MV output lands on the inline tier (outputs are delta-sized by construction). A framed direct-to-Parquet output path for oversized micro-batches is deferred.
- [ ] **MV — `/admin/views` sugar surface** `{#fut-mv-admin-views area:transform status:deferred from:2026-07-09-stream-continuous-design pr:- spec:-}`
  MVs register through the transforms admin surface (a `MicroBatch` transform body) in v1; a dedicated `/admin/views` CRUD surface is sugar.
- [ ] **MV — typed delta-fetch status mapping** `{#fut-mv-delta-typed-status area:transform status:deferred from:2026-07-09-stream-continuous-design pr:- spec:-}`
  The worker's abandon-vs-retry split on `fetch_mv_delta` keys off the `"mv delta:"` message-text prefix (the engine flattens the gRPC status through `client::be`). A non-prefixed deterministic fetch error (e.g. a mid-stream Arrow decode) retries to the queue's attempt cap before abandoning — wasteful but not a correctness hole (every retry re-reads from the committed watermark; the CAS stays the authority). A typed `mv_delta_status` mapper in engine-wire is the clean fix.
- [ ] **MV — lineage for empty / filtering micro-batches** `{#fut-mv-empty-lineage area:transform status:deferred from:2026-07-09-stream-continuous-design pr:- spec:-}`
  A micro-batch that produces no output rows (a filtering MV) advances the watermark and marks the run but emits **no lineage event** — the consumed-offset provenance lives only in the watermark, not in a lineage record. Emitting a rows-produced-zero lineage event (the worker already builds one) would close the provenance gap.
- [ ] **MV output tables get no admin catalog grant** `{#fut-transform-output-grant-mv area:transform status:deferred from:2026-07-12-catalog-dataset-acl-gating-design pr:- spec:-}`
  The per-dataset catalog ACL gating (`iss-catalog-lineage-acl-asymmetry`) moved the physical-output `Read` grant into the `POST /admin/transforms` define path, but only for a `Physical` body — `TransformBody::physical_output_grant_table` returns `None` for `MicroBatch`/`MicroBatchJoin`, matching the UI's prior Physical-only split and keeping this fix's scope. A MicroBatch/Join output is nonetheless a physical (untyped) log-stream table, so it stays invisible in the now-gated catalog / lineage to admins until manually granted — the same catalog-invisibility class the item closed for `Physical`. Fix shape: extend the grant to the two MV variants' bare-`TableRef` outputs (grant is idempotent + additive), or a single normalized "untyped output table ⇒ admin Read grant" seam over all bare-table output variants.

## iceberg

- [ ] **Iceberg-manifest bound decoding** `{#fut-iceberg-manifest-bounds area:iceberg status:deferred from:2026-06-21-iceberg-per-column-stats-design pr:- spec:-}`
  Stats are computed by re-reading the Parquet footer at write time; the bounds Iceberg already records in its manifest entries are not decoded. Reading manifest bounds directly (avoiding a footer re-read) is a deferred efficiency follow-up to `#road-iceberg-percolumn-stats`.
- [ ] **Footer-only / at-write-time stats reads** `{#fut-iceberg-footer-write-time-stats area:iceberg status:deferred from:2026-06-21-iceberg-per-column-stats-design pr:- spec:-}`
  The write path reads each file's full bytes via `FileIO` to compute stats — fine for local files, wasteful against S3. A footer-only range read (or capturing stats inline as the writer flushes the file) is deferred until a real object store (`#fut-iceberg-real-object-store`) makes the round-trip cost matter.
- [ ] **Pruning-aware cost estimates / join ordering** `{#fut-iceberg-pruning-cost-estimates area:iceberg status:deferred from:2026-06-21-iceberg-per-column-stats-design pr:- spec:-}`
  `IcebergMirrorTableProvider` skips files but does not surface per-column statistics into DataFusion's `Statistics` for cost-based planning (cardinality estimates, join ordering). Feeding the recorded bounds/null counts into the optimizer beyond file skipping is a deferred follow-up to `#road-iceberg-percolumn-stats`.
- [ ] **Full Iceberg schema evolution (field_id persistence + real-metadata evolution)** `{#fut-iceberg-full-schema-evolution area:iceberg status:deferred from:2026-06-23-iceberg-schema-evolution-design pr:- spec:-}`
  The additive slice (`#road-iceberg-schema-evolution`) is deliberately **mirror-authoritative**: an additive land writes superset Parquet and projects the new nullable columns into `iceberg_mirror.*`, but does **not** mutate the real Iceberg metadata schema (no `AddSchema`/`SetCurrentSchema`) — iceberg-rust 0.9.1 exposes no atomic schema-evolution+append transaction action. Consequence: loom-governed reads see the new column, but **external `ATTACH` clients reading the raw Iceberg table do not** — the same accepted gap class as `#iss-iceberg-inline-visibility`. A full-evolution slice would persist Iceberg `field_id` identity in the mirror (a new `field_id` column + reading Iceberg's schema list), evolve the real metadata schema, and unlock rename / drop / type-promote / reorder (all rejected today). Deferred until external-client visibility or non-additive changes are needed.
- [ ] **Additive schema evolution on the inline path** `{#fut-iceberg-additive-inline area:iceberg status:deferred from:2026-06-23-iceberg-schema-evolution-design pr:- spec:-}`
  The inline accumulation path (`inline_append`) currently does **detect + reject only**: an identical re-append is a no-op and any divergence (additive *or* non-additive) returns the typed `schema evolution unsupported` error. Additive evolution there is deferred — the common-case land path is the Parquet path (`#road-iceberg-schema-evolution`), and doubling the additive implementation onto the inline path wasn't worth it for this slice. A later slice could let inline accumulation absorb appended nullable columns directly instead of forcing a flush. Until that lands, an additive Parquet land is **rejected while live inline rows exist** (the caller must let the flush job run first), so the mirror's projected columns and the physical `inline_<tid>` table can never diverge — a divergence would otherwise break inline reconstruction on both the read and flush paths.
- [ ] **Time-travel as-of-schema reconstruction** `{#fut-iceberg-time-travel-schema area:iceberg status:deferred from:2026-06-23-iceberg-schema-evolution-design pr:- spec:-}`
  `iceberg_read.rs` builds the Arrow schema from `tbl.metadata().current_schema()`, so a time-travel read at a snapshot *before* a column was added still uses the current (wider) schema rather than the schema as-of that snapshot. The additive slice (`#road-iceberg-schema-evolution`) populates `iceberg_mirror.snapshot.schema_version` as the per-table schema generation precisely so a later as-of-schema read can resolve the correct generation against it; wiring that resolution into the read path is the deferred follow-up.
- [ ] **Schema cache for Iceberg serving engine** `{#fut-iceberg-schema-cache area:iceberg status:deferred from:2026-06-17-iceberg-datafusion-serving-engine-design pr:#82 spec:-}`
  `DataFusionServingEngine` registers all live tables per query (PG read + footer inference); a cache keyed by `(table, snapshot)` is a noted perf follow-up (YAGNI for now). Also covers the inline read-result cache deferred by `#road-df-postgres-tableprovider`: `PgTableProvider` re-queries Postgres for inline rows on every read (correctness — must see freshly-committed rows); memoizing the decoded batch by `(table_id, snapshot_id)` is the same `(table, snapshot)` follow-up, pursued only if repeated identical-snapshot latency is shown to matter.
- [ ] **Unify the iceberg/datafusion parquet-footer stats reader** `{#fut-iceberg-stats-dedup area:iceberg status:deferred from:2026-06-24-iceberg-arrow58-converge-design pr:- spec:-}`

That duplication was forced by the parquet 57↔58 type split (the `Statistics` enum is a distinct type per major) — removed by `#road-iceberg-arrow58-converge`, which put both readers on parquet 58. They can now collapse into one shared helper over the single `parquet 58` `Statistics` type, emitting the version-neutral `core::snapshot::{ColumnStat, StatValue}`. Deferred: behaviour-preserving cleanup, no consumer pressure; a candidate for the `loom-duplication-fix` routine.
