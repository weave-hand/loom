# Query API capabilities

The query-api service (`src/services/query-api/`) is loom's governed HTTP surface for reading and mutating typed objects: it resolves the ontology, compiles ACL policy into the SQL it generates (every caller value a bound parameter, never interpolated), and executes on the engine service — the sole serving path, running DataFusion against the Iceberg mirror — as a zero-DataFusion wire client over internal Flight SQL (`CommandStatementQuery`). It covers governed object reads with typed JSON rendering, relational link/multi-hop traversal, recursive `/graph` queries, a typed filter language, object sets and cursor pagination, governed write-back actions (insert/update/delete), and vector kNN search — all behind one deny-by-default governance spine.

_As of 879905ea._

## Governed object reads and typed JSON

`GET /objects/{type}` is the primary read: the handler resolves the ontology type to its physical table, gates the subject on `Read` (deny-by-default, and *before* existence is revealed — a denied subject gets 403 whether or not the type exists), folds the subject's policy into a row filter plus denied/masked column sets, compiles a `SELECT` over the allowed projection with the row filters ANDed in, and executes it on the engine. Masked columns render as a `'***'` marker; denied columns are absent. Identifiers come only from trusted ontology/ACL metadata (quoted via `quote_ident`, which escapes embedded quotes rather than panicking (#110)); request-supplied values always bind as parameters — the injection boundary every later slice preserved. The original slice proved this chokepoint chain end-to-end on an embedded DuckDB behind a swappable `ServingEngine` seam; the seam has since been repointed at the DataFusion engine over Flight SQL, and DuckDB is gone entirely — including the multi-file `LIMIT` corruption workaround that engine required (fixed with an `ORDER BY` barrier in #131, then deleted with the engine itself; the upstream-fix follow-up was dropped as moot (#205)).

Results are **typed objects**, not positional rows: the wire shape is `{"objects":[{prop: value, …}]}`, each value rendered by its property's declared logical type via the `core` `JsonRepr` classification. `Long` (int64) deliberately renders as a JSON string (values past 2^53 would silently round as JSON numbers — IDs routinely exceed that), `Integer`/`Double` as numbers, `Date`/`Timestamp` as ISO-8601 strings, and NULL as `null` regardless of type. An unknown logical type or a declared-type/value mismatch falls back to the cell's natural rendering — a permitted read never 500s on a rendering edge case.

Governed reads also feed a second wire: the Arrow Flight **export** listener (opt-in via `LOOM_FLIGHT_BIND_ADDR`, capped by `LOOM_EXPORT_MAX_ROWS`; typed `FlightExportTuning`) streams a governed typed-object slice out columnar (the ticket carries a loom `ExportCommand`, not SQL — the ACL'd SQL is compiled server-side per `do_get`, so a forged ticket is still a governed request). Its two knobs ride the same layered config seam as the SQL wire below (`defaults < file < env`, with a malformed bind address failing at startup naming the key) — with this, no raw-env corner remains in query-api's config surface.

A third TCP listener, `FlightSqlWireService` (opt-in via `LOOM_SQL_WIRE_BIND_ADDR`, capped by `LOOM_SQL_WIRE_MAX_ROWS`; typed `SqlWireTuning`), accepts a bearer-authenticated caller's own **arbitrary** SQL over the standard Flight SQL protobuf commands and forwards it to the engine's governed-SQL plane under a per-request `GovernedCatalog` resolved server-side from the subject's ACL — see the "Governed SQL over arbitrary queries, and external egress" section of [`engine.md`](engine.md) for the governance design.

## Derived properties

An `ObjectType` can declare derived properties that aggregate over one of its links — `Customer.orderCount = COUNT` of linked Orders, `totalSpend = SUM(amount)` — computed at read time as correlated subqueries appended to the object read's SELECT (FK and join-table link shapes both supported; COUNT/SUM coalesce to 0 on the empty set, AVG/MIN/MAX go null). Governance is both-ends: the subject must hold `Read` on the linked type and the linked type's row filters apply *inside* the subquery; if the linked type or the aggregated column is unreadable, the derived property is silently **omitted** (treated like a denied column), never an error. Derived properties are projected only — they are not filterable or sortable, and they are served on the plain object read, not on traversal output.

## Link traversal and multi-hop chains

Links are physically resolvable: `LinkDef` carries a `LinkBacking` — a direct foreign-key equijoin or a many-to-many join table — and `GET /objects/{from}/links/{link}` returns the linked target objects as one governed join. Governance composes across both ends: `Read` is required on source and target, the source row filter is ANDed into the join (closing the inference leak where a subject probes hidden source rows through a link), the target row filter and column projection shape the result, and source filter columns must be visible to the caller.

Multi-hop generalizes this to an ordered chain: `GET /objects/{from}/links?_path=l1,l2,…` (depth-capped at 4) compiles a single chain of INNER JOINs, with **every** hop type Read-gated (any denial → 403) and every hop's row filters ANDed in — the N-ends guarantee that a caller reaches final targets only through intermediate rows the policy permits. Only the final target is projected; the single-hop route is the `N=1` case of the same compiler. Caller filters address any position in the chain by link-name prefix (`?placed.status=open` filters the type reached via `placed`; bare keys filter the source), each coerced against *its own* type's declared property types and visibility-checked against *its own* projection. A per-hop filter naming a link that repeats in the path is rejected with a 400 pointing at `/graph` — the deliberate relational/graph boundary.

Every link is also traversable **backwards**, with no declared inverse link: inbound adjacency (`Ontology::links_to`) plus a pure column-role swap (`LinkBacking::reversed()`) let `?_direction=inverse` (single hop) and a `~` path-element prefix (chains) follow a link from its `to` side, governed identically at every hop. An inbound link name matching more than one link is an `AmbiguousLink` 400 — a governed read never silently picks.

## Object identity, association, and identity-keyed dedup

`ObjectType.identity` declares a single primary-key property (validated at bind: it must name a declared, required property). Identity unlocks three read capabilities. First, **association**: `?_shape=association` on the traversal routes returns the edge list itself — deduped `{from, to}` identity pairs typed by each end's logical type — instead of the flattened target set; both projected ends must have a declared, caller-visible identity (you cannot associate objects you cannot identify; intermediates need none). Second, **object sets** (`?_ids=`, below). Third, **correct dedup under masking** (#293): many-to-many traversal originally deduped with `SELECT DISTINCT` over the visible projection, which collapsed *distinct* objects into one row when ACL masked or denied the identity column. Dedup now keys on the raw identity **below the masking layer** — a windowed `ROW_NUMBER() OVER (PARTITION BY t_k.<identity>)` subquery whose outer select keeps the masked/visible projection, so the raw value never leaks but the object count is right; `identity: None` types keep the old `DISTINCT` fallback, and the single-table graph reachability compilers simply dropped their redundant `DISTINCT`.

## Graph queries

`/graph` serves what the relational chain structurally refuses — cyclic, self-link, variable-length paths — as depth-bounded `WITH RECURSIVE` CTEs (depth 1–10, default 5), governed inside the recursion and deduped by declared identity (which need only be *declared*, not visible: it is an internal CTE key). Four axes ship:

- **Bounded reachability** — `GET /objects/{type}/graph/{link}?depth=N`: the deduped set reachable via 1..N hops of a self-link, with the type's row filters applied at the seed, every recursive expansion, and the projection — a blocked intermediate cuts off everything beyond it.
- **Repeated path-cycle** — `GET /objects/{type}/graph?path=l1,…,lK`: a multi-link path that must return to the queried type, repeated up to N times; every intermediate type is Read-gated and row-filtered inside the recursive join. The single-link route is the 1-element case; a non-closing path is a `NotCyclicPath` 400. Since #287, path elements accept the `~` inverse sigil, so `memberOf,~memberOf` answers shared-membership with only one link declared — direction is resolved before compilation (via `links_to` + `reversed()`), so the recursive SQL and its cycle-safety are unchanged.
- **Multi-edge union** — `?links=l1,…,lN`: each recursive step follows *any one* of a set of self-links (FK and join-table freely mixed), compiled as a `UNION ALL` edge relation inside a single recursive step (a DuckDB/DataFusion recursive-CTE constraint allows only one self-reference). `?path=` and `?links=` are mutually exclusive.
- **Recursive core + relational tail** — `?path=knows*,worksAt`: a `*`-suffixed self-link core (the recursion) glued by reachable-set membership to a fixed forward chain landing on a possibly different projected type — "the companies of everyone reachable through `knows`" — in one SQL statement, with the core governed in the CTE and each tail type governed at its alias.

The set routes answer membership only; `?tree=true` on the self-link and path-cycle routes returns the **shortest-path tree** instead (#288): per reachable node, its BFS depth and a parent pointer, settled deterministically (min depth, then min parent identity — scan-order independent), roots included, as a distinct `{roots, nodes}` shape. The per-node depth also delivered the min-depth annotation for the tree shape (#288). Because the tree *projects* identity as `id`/`parent`, it requires a visible identity (masked/denied → 403) — stronger than the set reads.

## Filter language

Every read shares one typed, governed predicate grammar. A query-param key names a column (or `<link>.col` for a chain position); the value carries the operator as `op:operand` — bare value = `eq`; `ne`/`lt`/`le`/`gt`/`ge`; set ops `in:`/`nin:` (comma-separated, with `\,`/`\\` escaping so a literal comma or backslash in a string operand is representable (#145)); bare-token null ops `isnull`/`isnotnull`; and, from #285, `between:lo,hi` sugar and case-insensitive text-pattern ops `contains`/`startswith`/`endswith` (string-only, rendered as `ILIKE` over a bound operand with LIKE metacharacters escaped — a literal `%` matches the character; raw caller wildcards are deliberately not offered). An `eq:` prefix escapes a literal value that would otherwise parse as an operator.

The discipline is **visibility-then-coerce**: a filter column must be in the caller's allowed, unmasked projection *before* the value is parsed (so no operator can probe an invisible column), then each operand coerces to the column's declared logical type — a `Double` filter binds a real double, a `Date` an actual date, never a text comparison. Repeated keys AND together (a `ge:`+`le:` pair is a range). Cross-column disjunction arrived in #289: a reserved `_or` param carries ≥2 member predicates (`col:op:rest`, comma-separated), rendered as one parenthesized OR-group inside the existing AND spine; members reuse the full operator grammar and per-member visibility checks, and governance conjuncts — row filters, `_ids`, ACL — stay strictly ANDed above any OR-group, so disjunction can never weaken a security predicate. `_or` is wired on the object-read endpoint only. Caller predicates always narrow within already-permitted visibility; they never widen access.

## Object sets and reserved control params

`?_ids=1,2,3` scopes any read — plain object read, single-hop, chain, association, and the graph seeds — to a caller-supplied object set addressed by the type's declared identity, lowering to an ordinary `In` predicate on the identity column (so it inherits filter governance verbatim; no identity → 400). All control params live in a reserved `_`-prefixed namespace (`_ids`, `_or`, `_path`, `_direction`, `_shape`), and bind rejects any property or derived-property name starting with `_`, making a control-param/column collision impossible by construction.

## Cursor pagination and type listing

`GET /objects/{type}?limit=&cursor=` pages the object read with a forward-only keyset: `ORDER BY <identity> ASC`, a `> cursor` keyset predicate, fetch `limit+1`, return `{objects, next}` (`limit` clamped to [1, 200]; `next` null on the last page). The path is fail-closed by construction — five 400s fire *before* any SQL or cursor is emitted: no declared identity, a masked/denied identity (a cursor over an unreadable column would leak it), a non-round-trippable identity type (only `Integer`/`Long`/`String`), `_ids` combined with pagination, and a malformed cursor. The default un-paginated read is byte-identical to before (no `ORDER BY`). Alongside it, `GET /ontology/types` lists object-type names via a `gov_list_types` engine-wire RPC — auth-required but not per-type ACL-gated, since the type catalog is ontology metadata (the object *data* stays governed behind `/objects/{type}`). `GET /ontology/types/{name}` (#346) serves one type's full shape — table binding, identity, properties with required flags, derived (aggregate-over-link) properties, declared vector indexes, and outbound + inbound links — over the same wire-capable reads (`gov_get_type`/`gov_links`/`gov_links_to`/`vector_indexes_for`), 404 on an unknown type; it is the UI Schema-tab read. The type, each property, each link, each derived property, and each vector index also carry an optional `description` when one is defined (omitted from the JSON when absent), the read half of `road-ontology-semantic-descriptions`; the same descriptions flow into the generated OpenAPI document (see [control-plane.md](control-plane.md) → *Ontology and typed writes*). The `derived[]` (`{name, ty, link, agg, description?}`) and `vector_indexes[]` (`{name, property, metric, spec, description?}`) arrays complete that read surface (#455): before it, `DerivedPropertyDef.description`/`VectorIndexDef.description` were write-only — settable via `POST /admin/models`, invisible on every read. Vector indexes are name-sorted for a stable order (`vector_indexes_for` leaves it unspecified); and because derived properties *are* served as columns on object reads, the per-type OpenAPI **read** component schema now declares each as `readOnly` (they never enter the write/action request schemas) — fixing the standing inaccuracy where the generated document omitted derived columns the rows actually carry. Dataset metadata is browsable the same way: `GET /datasets` lists the live mirror tables and `GET /datasets/{schema}/{table}` returns the current snapshot id/time plus the column schema at exactly that snapshot (a self-consistent pair), served through `WireControlPlane::catalog()`'s direct-plane delegation — the queue/lineage precedent — so no catalog RPCs were added (#346). These three catalog reads (`GET /datasets`, `GET /datasets/{schema}/{table}`, and `.../preview`) are **per-dataset ACL-gated** under the *same* readable predicate `/lineage` enforces — Table `Read` allow **or** any backing ontology type's `Read` allow — lifted out of `LineageVisibility` into a shared `DatasetVisibility` governor both consumers construct per request (one resolution, one soundness argument). `GET /datasets` filters to the tables the subject may read (no grants ⇒ empty list); the two point reads return a single canonical **404** for an unreadable dataset that is *byte-identical* to a genuinely nonexistent one — the point-read analog of the lineage seed gate's empty page, deliberately not an existence oracle (`DatasetVisibility` never consults the catalog, so an existing-but-unreadable table is indistinguishable from a missing one). This closes the catalog/lineage governance asymmetry: a subject now sees a dataset in the catalog reads, its preview, and its lineage node under exactly one predicate. Preview keeps `SELECT *` semantics for readable datasets (per-row/column governance on preview is the narrowed `#fut-ui-dataset-preview-acl` residue). Catalog views (`#road-catalog-views`, PR #438 — see [control-plane.md](control-plane.md) → *Catalog views*) share this same `(schema, name)`-addressed dataset surface: `GET /datasets` gates a view identically to a physical table (`is_table_readable` already resolves a view ref — a `Table` grant on the view or a `Read` grant on any type bound to it) and lists it with `"kind": "view"` plus its physical `"base": {schema, name}` (`updated` delegates through `current_snapshot` to the base); `GET /datasets/{schema}/{table}` likewise carries `kind`/`base` on a view ref, its snapshot/column-schema response delegated to the base through the same `Catalog` methods every other reader uses. `PolicyTarget::Table(view_ref)` grants work exactly like a grant on a physical `TableRef` — the exact-match ACL check is the whole decoupling: a role holding `Read` on the view sees it, with no bearing on the base's own grants. Relatedly, `POST /admin/transforms` now grants the reserved `admin` role `Read` on a **physical** output table server-side as part of the define flow (replacing the UI's best-effort client-side self-grant, now deleted), so a physical transform's output is visible in the catalog and lineage regardless of the defining client; typed outputs need none (their visibility rides the bound type), and MV (`MicroBatch`/`MicroBatchJoin`) outputs are the residual `#fut-transform-output-grant-mv`. Closes `iss-catalog-lineage-acl-asymmetry` (#431). Each `GET /datasets` entry also carries a cheap **`rows`** count for physical tables — the exact live row total at the current snapshot, computed by a single `Catalog::row_count(table, at)` port method that pushes a `SUM(record_count)` aggregate over the data files live at that snapshot into SQL in the postgres adapter (the same MVCC window `Catalog::files` walks, one `query_scalar!`, no file rows materialized to the caller) and folds the same live set in the memory fake; it is `null` for **views** (a base-file sum would over-count a filtering view — deliberately not computed) and on any count fault (best-effort `.ok()` — a count hiccup never 500s the list, and `0` is a *known-empty* table, distinct from `null` = unknown). The UI Catalog list renders it K/M-scaled via `format_count`, falling back to `—` only when the count is absent (#618). `GET /datasets` also accepts optional **server-side list controls** (#619): `?sort=name|project|updated|rows` with `?dir=asc|desc`, and `?project=<schema>` to filter to one project. An absent `sort` preserves the natural `(schema, name)`-then-views order, so existing callers are unaffected; an unknown `sort`/`dir` token is a **400**. The controls are a pure, socket-free `dataset_list` module (`from_params` → the 400 message; `apply` filters by exact project then stable-sorts with a direction-independent `(schema, name)` tiebreak) applied to the **already-ACL-gated** entry list the handler collects — no new SQL, no `.sqlx` change, and no bypass of the readable predicate (the sort/filter only ever reorders/narrows rows the subject may already see). The Catalog UI drives these via project filter chips + Sort key/direction buttons that re-fetch server-side (see [ui.md](ui.md)).

## Time-travel reads (as-of)

Both `GET /objects/{type}` and `GET /datasets/{schema}/{table}` accept two mutually-exclusive time-travel selectors: `?as_of_snapshot=<i64>` names an exact mirror snapshot id, and `?as_of=<rfc3339>` resolves to the latest snapshot at or before that timestamp, for the read's backing table. Resolution happens **query-api-side**, not on the engine: the handler turns the selector into a concrete `SnapshotId` (the timestamp form via `Catalog::snapshot_as_of`), then ships that resolved id to the engine on a dedicated `AsOfStatementQuery` Flight ticket — a parallel surface to the standard `CommandStatementQuery` interop path, which stays untouched for callers that never ask for time travel. A malformed selector, or both selectors supplied together, is a 400; a well-formed selector that resolves to nothing (a pre-history timestamp, or an id absent from the table's snapshot history / at which it is not live) is a 404; a selector that resolves to a snapshot older than the GC retention horizon is a **410 Gone** (see below).

Both routes validate `as_of_snapshot` the same way: exact **snapshot-history** lookup via `Catalog::snapshot(table, id)` — the id must exist in the mirror's global snapshot history *and* the table be live at it, so an id above the table's current snapshot (or one it never had) 404s on both surfaces. This one indexed lookup replaced the object path's former open-ended-upward liveness-range check (which read *live* for above-current ids) and the dataset path's O(history) scan, unifying the two on the same primitive.

**Retention horizon (410).** A selector below the GC retention horizon `H` no longer 410s unconditionally — `ensure_within_retention` (`query-api/src/handler.rs`) now conjoins a cheap fast path with a precise per-table check, so an append-only table's history reads back forever while a table whose visible rows were actually destroyed (or are about to be) still refuses the read. Two tiers, cheapest first:

1. **`at >= H` is the zero-query fast path**, unchanged: `H = max(snapshot_id) WHERE snapshot_time < now() − LOOM_GC_RETENTION_SECS` — the exact derivation `iceberg_gc` reclaims under, shared via `Catalog::snapshot_horizon` — and a read at or above it is provably complete with no further query (a reclaimable row has `end <= H <= at`, so it was never visible at `at`). This remains the overwhelmingly common case.
2. **Below `H`**, the guard calls `Catalog::snapshot_intact(table, at, H)` — a two-clause conjunction, per table **incarnation**:
   - *Watermark:* nothing visible at `at` was **already** destroyed. GC durably records `iceberg_mirror.table.reclaimed_through` (migration `0045`) — the highest `end_snapshot` it has physically reclaimed for that incarnation, bumped inside the same commit as its deletes (see [control-plane.md](control-plane.md) → *Catalog and the Iceberg mirror*). Before this, reclaimed-ness was recorded nowhere, which is exactly why the old guard had to fall back to the table-independent `at < H` proxy.
   - *Eligibility:* no **surviving** row visible at `at` is eligible for destruction (`begin <= at < at's row end <= H`), checked across both the data-file tier and the dynamic `inline_<tid>` tier. This clause is what makes the verdict independent of whether GC has actually run, and what closes the race with a GC committing concurrently with the read.

   Only if neither clause fires is the read served. Net effect: a below-`H` read of a table whose visible-at-`at` rows were never end-capped (append-only, or simply not rewritten since) now returns **200** instead of 410; a table whose rows were end-capped (or are eligible to be) still 410s.

**The obvious "quiet table" simplification is UNSOUND — do not reintroduce it.** The natural-seeming alternative ("has anything been written since `at`? if not, serve") is exactly what this guard must NOT do. A governed delete-all routes through `overwrite_truncate`, which end-caps every live data file *and* every live inline row and writes no new row of any kind. GC then reclaims them. The surviving mirror state is a live `table` row, its `column` rows, and **zero** data files — so any predicate computed from surviving rows alone reports the table as quiet, and a "quiet ⇒ serve" guard would serve **0 rows** where the data used to be: a loud 410 silently becomes silent data loss. `postgres/tests/timetravel_intact.rs::truncate_is_not_quiet` pins this case at the catalog level. `Catalog::snapshot_intact`'s two clauses above are the actual sound test; a future reader must not "simplify" the guard back to a quiet-table check.

**Clause order is load-bearing, not stylistic.** `snapshot_intact` evaluates the eligibility clause (evidence) BEFORE the watermark clause, on one connection, strictly ordered in time. Reading the cheap watermark first is unsound: it returns "nothing reclaimed yet", a concurrent GC then commits — destroying a row visible at `at` and bumping the watermark together, in the same transaction — and the later evidence read finds nothing eligible **because it was already destroyed**, so both clauses pass and an incomplete read is served. Evaluating evidence first and watermark last makes the pair a complete detector: whichever side of the evidence read GC's commit lands on, at least one clause observes it. Do not reorder this for the watermark's cheaper cost.

**The engine has no parallel guard.** `EngineTicket::AsOfSql` → `do_get_as_of_sql` (`src/services/engine/src/flight.rs`, ~:102-117) runs no retention check at all — **query-api is the sole enforcement point** for time-travel retention. That is fine while the Flight SQL surface between query-api and the engine is internal-only, but it becomes a real gap the moment the external SQL wire (deferred — see the project status header) exposes that surface to a client that can bypass query-api.

**Two caveats inherited from the original design, not introduced here:**
- `H`'s derivation assumes snapshot-id order tracks `snapshot_time` order; ids and times can invert under concurrent long-running writers. GC and the guard share one derivation (`iceberg_mirror::horizon_before`) so they can never disagree *with each other*, but neither can correct for an inversion.
- `H` advances while a read is in flight, so a row with `end` just above `H` at guard time can become eligible moments later. This is not new — today's `at >= H` fast path has the same exposure — and this change does not close it.

Clause 2 of `snapshot_intact` is also deliberately **coarser** than GC's real victim set: it ignores the MV read-position floor (`mv_floor`), so a row GC would currently *hold back* for a lagging MV can still read as "eligible" here. That only makes the guard more conservative (it can refuse a read that would in fact have completed, never serve an incomplete one), so it is safe — do not tighten clause 2 to match GC's floors.

The guard reads query-api's own `LOOM_GC_RETENTION_SECS`, while the reclaimer (`gc_table`) runs in the engine service reading *its* copy — deploy both services with the same value (they share the 7-day default) so the guard's horizon matches what GC actually reclaims under. It runs only on the selector-present path; no-selector live reads are unaffected. Time-travel reads also inherit the existing as-of-schema gap: the served Arrow schema is always the table's *current* schema, not the schema as of the selected snapshot (`#fut-iceberg-time-travel-schema`).

## Actions: governed insert, update, delete

`POST /actions/{name}` invokes a named ontology `ActionDef` against its target type — the governed write-back path, and the first live `Action::Write` enforcement. The JSON body parses against the action's declared parameters per logical type (`Long` as a string, `Date`/`Timestamp` as ISO strings — the exact inverse of the read renderer); required params must be present and non-null, unknown keys are rejected, and an action definition that no longer conforms to its target type is a distinct `Misconfigured` server-side fault rather than an opaque 500. Governance is two-layer: the coarse `Write` ACL gate, then fine-grained enforcement on the **affected row** — a pure, fail-closed in-memory evaluation of the policy's row filters against the concrete row (three-valued SQL semantics: an UNKNOWN verdict denies, mirroring how an UNKNOWN `WHERE` row is excluded from a read), plus column-level denial. Per-value model constraints (range/length/pattern/one-of declared on `PropertyDef`) run on the same resolved row and reject with a 422 naming the failed rule (#265) — the same `core` validator ingest's land gate uses, so both write paths enforce identical rules. Writes commit atomically with their lineage event through the engine and return the action's `run_id`. A single-step action's success body is the bare affected object with a **kind-true** status (`201 Created` for Insert, `200 OK` for Update/Delete — the status keys on the primary step's kind; #397); a **multi-step** action — one that commits several typed writes atomically in one transaction (e.g. `createOrderWithLines`: an `Order` plus its `LineItem`s, cross-step foreign keys resolved through named `bind`s) — returns an ordered `{steps:[{bind,target,objects}]}` envelope carrying **every** step's affected row, each labelled by its declared `bind` (when it declared one) and `target` type, with array order disambiguating unbound same-target steps (#396). The `X-Loom-Run-Id` header carries the run id for both shapes. Any action — single-step **Insert**, **Update**, or **Delete**, and **multi-step** — may declare `downstream: Vec<JobTemplate>` — on commit each template (`kind` from the worker job-kind allowlist, validated at define time; a JSON `payload` whose `@self.<prop>` leaves resolve against the action's **written row**) is enqueued as a `NewJob` **atomically with the write** (the job is visible to a worker iff the write commits — rollback ⇒ no job for every kind, proved e2e for Insert/Update/Delete's inline-delta rejection paths), the write-then-derive primitive (slice 4). `@self.<prop>` resolves against the **primary step's produced columns** — the columns its `parameters` (each bound via `ParamDef::binds_property`) and `assignments` actually set, identity included — not the target's full property schema; a ref to a property the primary step does not write is **rejected at define time** (`validate_action_downstream`), so a template accepted at define time is guaranteed to resolve rather than silently degrading to its literal `@self.<prop>` string at invoke time. For a multi-step action `@self` is scoped to the **primary** (first, identity-bearing) step only — cross-step `@bind.prop` references into `downstream` templates stay out of scope (`#fut-action-cross-step-expr-refs`). On the whole-table copy-on-write **overwrite** path (identity-less types, or COW's non-inline fallback), declared `downstream` jobs merge into the same commit alongside any auto-enqueued vector-index rebuild jobs (#240) — one `Vec<NewJob>` rides the overwrite's single commit tx, so the same commit-or-neither contract holds there too.

Beyond insert, `ActionKind` covers `Update` and `Delete` (#208): update is an identity-targeted PATCH (locate by declared identity, apply the field delta, recommit), delete removes the object — originally via whole-table copy-on-write, made O(change) for identity-bearing types by the inline-shadow rework (#331): a mutation writes one inline delta row (version or tombstone) that the engine's merge-on-read resolves below the governed layer, with a per-identity CAS closing the read→commit race (identity-less types keep whole-table COW). Actions also carry declarative custom logic: a param can bind to a differently-named property and an `ActionDef` can carry constant assignments (#269), and a property can be set by a **computed assignment** (#322) — a closed, total, injection-free expression grammar (literals, param/`@property` refs, arithmetic, string concat, comparisons, `if/then/else`, and a whitelisted function set incl. `now()`), type-checked at define time and evaluated to a plain value *before* the unchanged ACL and constraint gates, so computation cannot weaken governance; runtime arithmetic faults (division by zero, bad cast) are a 422, not a 500.

## Catalog views: view-aware typed writes

A type bound to a catalog view (`ObjectType.table` naming a view rather than
a physical table) writes through the view — insert/update/delete — with the
write physically **lowered to the view's base** and additionally gated by the
view's own predicate, on top of the unchanged ACL and constraint gates
(`#road-catalog-views`, PR #438). `resolve_write_base` resolves a step's
target once: when `target.table` names a view, the physical write base is
the view's `base` (every engine RPC — the version probe, the delta write, the
whole-table `Overwrite` — must land there, since the engine's writer is purely
physical and mints a mirror table under whatever ref it is handed), and the
view's `predicate` rides along as an **additional** row-filter gate; a plain
table has no view and behaves exactly as before. Because the write row is
always expanded to the target type's full declared property set before the
predicate is evaluated (`view_row_admits`, three-valued and fail-closed — an
UNKNOWN predicate result denies, never admits), a caller can never commit a
row that then falls outside the view it wrote through:

- **Insert**: the full post-image row is checked against the view predicate
  before commit; a row that would land outside the view is `Forbidden` (403).
- **Update/Delete** (the single-object inline-delta path, `run_mutate`): the
  target is located **through the view name**, so an out-of-view identity is
  already invisible (0 rows ⇒ `NotFound`) before the predicate check ever
  runs; the check itself is then belt-and-braces. An UPDATE's post-image is
  additionally re-checked (leg 3) — a caller may not PATCH a row *out of* its
  own view — denied as `WriteDenied(RowFilter)`.
- **Multi-step actions** (`govern_and_build_mutate`): the multi-step path must
  read the physical **base** table directly (its whole-table `Overwrite`
  would otherwise silently drop every out-of-view row it doesn't re-read), so
  unlike the single-object path it *can* locate an out-of-view identity.
  Surfacing that as a 403 there would let a caller distinguish "exists but
  denied" from "doesn't exist" for identities outside their view — an
  **existence oracle through the view**. Leg 1 therefore surfaces the same
  `NotFound` (404) the single-object path gives for an invisible row instead,
  keeping the two paths' observable behavior identical; leg 3 (the
  post-image escaping the view) is unaffected either way, since the row was
  visibly the caller's before the write.
- The same-table multi-mutation **clash guard** (a multi-step action may not
  Update/Delete the same physical table from two different steps, since the
  staged `Overwrite` reads pre-action state) compares each step's **resolved
  base**, not its bound `TableRef` — so a view and its own base, or two
  sibling views over one base, clash exactly as two steps naming the same
  table would.

Because the engine always scans the physical **base** (a view expands to
`SELECT … FROM base`), the base's merge-on-read must know its identity column even
when the ONLY type is bound to the view. `identity_for_table` therefore resolves
identity from a type bound directly to the scanned ref **or** to a
`dataset_view.view` whose base is that ref, so a view-bound-only type's UPDATE
inline delta still shadows the old base file row and its DELETE tombstone still
hides it — no base-bound "crutch" type is required. (`stream_meta_for_table` /
`version_for_table` are left keyed on the physical base's own live `table_id`,
which is already correct: CDC-ness is a property of the base table, not the view
binding, and views over CDC bases are out of scope for this slice — see
`#fut-view-stream-subscribe`.)

The admin surface (`src/services/runtime/src/admin.rs`, both OpenAPI drift
guards): `POST /admin/views` defines a view (create-only, 201; the request
body carries the base ref, an optional `RowFilter` predicate, and an optional
column projection) and `DELETE /admin/views/{schema}/{name}` drops one (200,
or 404 unknown) — both behind the `require_admin` gate.

## Vector search

`POST /search/{type}/{index_name}` serves governed kNN over a declared vector index (#227): the body carries the query vector, `k`, and optional `nprobe`/`ef_search` knobs; column, metric, kind, and dimension resolve server-side from the named index (a wrong query dimension is a 400, an unknown index a 404). The result is a ranked `{id, distance}` list — ids and distances only, so no column masking applies; clients hydrate via `/objects`. Governance is the coarse type-level `Read` gate plus a row-filter **post-filter**: the engine's top-k ids are re-checked against the subject's row filters through a governed id-projection read, so a caller never sees an id their policy hides (the result may return fewer than `k`). For an identity-bearing vector type this survivor post-filter runs **unconditionally** (not only when a row filter exists) and keeps one hit per surviving identity — so a COW inline-shadow UPDATE's stale cold-index duplicate collapses to a single hit and a DELETE's tombstoned cold hit is dropped, the re-query reading the engine's live merged view (precedence-winner, tombstone-hidden) as the source of truth for which identities are live (#400; was an interim query-time mitigation — durable cold-entry removal now lands with slice-2 compaction consolidation: the consolidation fold's `overwrite_parquet_snapshot_consuming` commit enqueues one deduped `build_vector_index` rebuild per index declared on the table via the same `rebuild_jobs_for` seam the flush/overwrite paths already share, so a stale cold-index entry is durably removed rather than only masked at query time). Freshness is maintained by auto-rebuild on flush (#240): end-capping inline vector rows enqueues a deduped index rebuild so just-flushed vectors do not silently vanish from results.

## Governed ad-hoc SQL console (`POST /sql`)

`POST /sql` runs a bearer-authenticated subject's **arbitrary read-only SQL** and returns `{columns, rows, truncated}` (every cell a display string, `""` for NULL) — the client-facing half of the external-SQL-wire's governed execution substrate, exposed over HTTP for a query console (#621). The request body is `{sql, limit?}`; `limit` defaults to 1000 and is capped at 10000. **Governance and read-only-ness are enforced in the engine by construction, not by parsing the client's SQL:** the handler resolves the subject's `GovernedCatalog` **server-side** (`resolve_governed_catalog` — never accepted from the wire, exactly as the Flight SQL wire's `do_get`), and `EngineServingClient::execute_governed` forwards the SQL to the engine's `execute_governed_sql_stream`, which registers **only** the granted types' tables as governed read `TableProvider`s (row filters ANDed, denied columns dropped, masked columns rendered as `***`) in a throwaway `SessionContext`. A subject therefore can never name a table it holds no grant on — the engine's closed-world catalog makes an ungranted or unbound table indistinguishable from a nonexistent one — nor observe a denied column, an unmasked value, or a filter-excluded row, regardless of how the SQL is written (a JOIN, GROUP BY, or subquery carries the same governance). There is no persist path (the governed providers implement only `scan`), so DML/DDL simply fails to plan. A result exceeding the row cap is truncated with `truncated: true` (the response is bounded, unlike the Flight wire's stream cap which errors). Errors: a plan/validation fault — malformed SQL, or a table the subject cannot see — is a **400** carrying the engine's own plan message (safe to echo: it is the caller's own SQL vocabulary); an empty body is a 400; a coarse denial is a 403; a backend fault is an opaque 500 logged server-side. This is the reusable-`SqlEditor` console's backend; the surface consuming it is the UI **Query** surface (see [ui.md](ui.md)).

## Error contract and governance behaviour

The status mapping is uniform across reads: 403 `Forbidden` for any Read/Write denial, issued *before* existence is revealed (and for an empty permitted projection, or a tree/association read whose identity is governed); 404 for a genuinely unknown link or index (an unknown *type* on an object read is unreachable as a 404 — the Read gate denies before existence, so it returns 403; the 404-for-unknown-type case applies to the ontology type-shape read `GET /ontology/types/{name}`, which is not per-type ACL-gated); 400 for the caller's request faults — bad filters, malformed chains and non-cyclic paths, ambiguous inverse links, depth/pagination violations; and an opaque `"internal error"` 500 for backend faults, whose detail is logged server-side rather than leaked (#140). Since #284, an uncoercible filter value returns a structured 400 body — `{"error":"bad_filter_value","column":…,"expected":…,"value":…}` echoing the expected logical type and the caller's own rejected operand — while visibility denials stay a bare column name (a permission signal never echoes a value); and `POST /actions` returns **422** for well-formed bodies that fail semantic parameter validation (missing/mistyped params, aligning with the constraint-violation 422 on the same path), reserving 400 for malformed JSON. The 400 classification is reserved for *caller-supplied* values: an engine-derived fault in `/search`'s row-filter post-filter — a mirror-returned hit identity that fails to coerce to its declared logical type, or a served vector type with no declared identity — is server-data-integrity, not caller-forgeable, so it classifies at its source (`QueryError::Internal`) as an opaque **500** with a single server-side `tracing::error!`, never a caller 400 echoing engine data (#339). The load-bearing invariants, held everywhere: deny-by-default; governance compiled into the SQL itself (row filters ANDed at every position, projections applied at compile time), not post-filtered in the app except where a design demands it (vector search); caller input only ever narrows; and every caller value is a bound parameter.

## Known gaps

- `#fut-ontology-types-pagination` — `/ontology/types` returns one unbounded page; honour cursor+limit if ontologies grow.
- `#fut-object-read-nonidentity-sort` — pagination orders by ascending identity only; no descending or arbitrary-column sort.
- `#fut-traversal-keyset-pagination` — traversal/graph-tail reads are unordered; no stable order + cursor over them yet.
- `#fut-composite-identity` — `identity` is a single column; multi-column natural keys fall back to `DISTINCT` dedup.
- `#fut-mandatory-identity` — identity stays opt-in; the `identity: None` `DISTINCT` fallback lingers until it is required.
- `#fut-scalar-derived-props` — no own-column/expression derived properties; needs a whitelisted expression surface.
- `#fut-derived-on-traversal` — derived properties serve on `read_object` only, not traversal/chain output.
- `#fut-multi-hop-aggregates` — no aggregates over a link chain, no derived-on-derived.
- `#fut-derived-materialization` — derived properties are read-time subqueries; no materialization for hot paths.
- `#fut-derived-filter-sort` — derived properties are not filter or sort targets.
- `#fut-or-link-graph-endpoints` — `_or` groups work on the object read only, not link/graph endpoints.
- `#fut-or-set-operand-escaping` — a literal backslash escape inside an OR-member set operand double-unescapes to a clean 400.
- `#fut-or-nested-predicates` — one level of OR under a top-level AND; no nested boolean predicate trees.
- `#fut-inverse-in-union` — the `?links=` union axis takes forward self-links only; no `~` members.
- `#fut-inverse-in-tail` — the `*` recursive core and its relational tail are forward-only.
- `#fut-graph-single-hop-direction` — the legacy `/graph/{link}` route ignores `?direction=`; `~` in `?path=` is the sole graph inverse surface.
- `#fut-graph-filter-addressing` — no per-occurrence/positional filter addressing for repeated links (the `/links` 400 case).
- `#fut-weighted-edges` — reachability and trees are unweighted (fewest hops); no min-cost traversal.
- `#fut-tree-union-tail-routes` — `?tree=true` covers the self-link and path-cycle routes only; union and core+tail trees are 400.
- `#fut-tree-materialized-paths` — parent pointers only; no materialized full paths, k-shortest, or all-shortest enumeration.
- `#fut-set-depth-annotation` — the flat reachable-set response carries no per-node depth (the tree does).
- `#fut-governed-scan-pushdown` — the governed table provider pushes no client projection/filter/limit into the inner scan yet.
- `#fut-view-stream-subscribe` — no stream/CDC subscribe on a catalog view; `declare_stream`/`GET /objects/{type}/changes` resolve a `TableRef` as a physical table only.
- `#fut-query-multitype-joins` — no multi-type queries/joins, schema sidecar, or timezone-aware timestamps.
