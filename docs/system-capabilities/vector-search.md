# Vector search capabilities

loom stores embeddings as governed, lineage-tracked data and serves k-nearest-neighbour search over them: a first-class `vector(N)` column type, named vector-index declarations in the ontology, engine-side index builds (exact Flat plus approximate IVF-Flat and HNSW) persisted as Apache Puffin sidecars bound to Iceberg snapshots, a governed external `POST /search` endpoint on query-api, and automatic index rebuilds triggered by the flush that stales them. This document describes what exists today, its behaviour and guarantees, and the known gaps.

_As of 4861433b._

## Vector column type and index codec

The `vector(N)` column type (#168) is loom's first parameterized, non-primitive logical type: `BaseType::Vector(u32)` carries the dimension, with a `vector(N)` string codec so the dimension round-trips through the mirror's existing `column_type` strings — no new catalog column. The element type is fixed `f32`. On the wire, landing accepts either Arrow `FixedSizeList(Float32, N)` or `List<Float32>`, validates every row's element count against the declared `N` (a width mismatch is a deterministic bad-input rejection), and normalizes to `List<Float32>` before the Iceberg write — the shape the pinned iceberg-rust writer supports and Parquet round-trips cleanly. Storage is Iceberg `list<float>`; `N` is a loom-level constraint remembered in the mirror. Vector columns carry no per-column stats (Iceberg bound serialization is primitive-only) and are non-filterable/non-sortable. Read-back is value-exact via the columnar Arrow path; the per-object JSON read (`GET /objects/{type}`) skips vector properties (deferred, see Known gaps). The Iceberg path is the only storage backend; DuckLake is deferred.

The inline (hot) tier stores `vector(N)` cells too (#209): Postgres `real[]` (native f32 — exact by construction, ~4 bytes/element vs jsonb's decimal text), with a shared `mirror_column_type` helper keeping the cold and inline column-type projections in sync. A drifted copy of that conversion in the engine's inline PG provider dropped vector columns from SQL reads over live inline rows; it was deleted in favour of the shared decoder (#301), which also standardized the Arrow list-child name on `item`.

Every index serializes to one compact self-describing binary (`magic "LVIX" | version | metric | kind | …`) written into a `loom-vector-index-v1` Puffin blob; `decode(bytes)` dispatches on the `kind` byte to the concrete deserializer, so the mirror's `index_kind` column is observability only. The decoders are hardened against corrupt blobs: the HNSW decoder bounds every untrusted `Vec::with_capacity` against the bytes remaining, rejects out-of-range entry points and neighbor indices, and enforces the graph-height invariant that makes every descent access in-range (#215, #216); the Flat/IVF decoders got the same bounded-allocation guards (#219). The codec itself was extracted into a shared module — `core/src/vector_index/{mod,codec,flat,ivf,kmeans,hnsw}.rs`, with `codec.rs` owning the header/f32-section/keys read+write and `pack_rows` — with byte-identity proven by golden-blob characterization tests and zero public-API change (#303). The mirror queries backing the index binding are compile-time sqlx, covered by build-time schema verification (#207). The identity block's single-key-kind invariant is enforced, not assumed: `pack_rows` rejects mixed `Int`/`Str` identity keys at build as a `Validation` error, and every decoder requires full buffer consumption after the identity block, so a padded or mixed-kind blob is a loud decode error instead of silently misparsed identities (#335).

## Index definition in the ontology

A named vector index is a first-class ontology object (#223). `define_vector_index` (an `Ontology` trait op, upsert semantics like `define_type`) persists a `VectorIndexDef { name, type_name, property, metric, spec }` to `ontology.vector_index_definition`; validation requires the property to exist and be a `vector(N)` type, and the dimension is never restated — it derives from the property. **Multiple named indexes per property** are supported (e.g. an HNSW `by_sim` for similarity and an IVF-Flat `by_cluster` for grouping), enforced by the `(type_name, name)` primary key; the mirror's `iceberg_mirror.vector_index` PK gained `index_name` so materialized indexes coexist per column. The declaration is the single source of truth for kind/metric/params: `BuildVectorIndexJob` shrank to `{schema, name, index_name}` and the build primitive resolves the named declaration. The read path resolves by name against the mirror row (no ontology lookup at query time). Declaring an index does not build it, and there is no drop operation yet — redeclaring a name replaces its spec (see Known gaps). Definition ops rode the internal/programmatic `define_*` surface only until the admin HTTP surface caught up (issue #363, PR #NN): `POST|GET /admin/models/{type}/vector-indexes` now declares and lists a type's named indexes over HTTP, admin-gated like the rest of `/admin/models` (no new ACL beyond the existing admin-role gate). The request body is `{name, property, metric, spec}` with `spec` deliberately parsed stricter than `IndexSpec::from_label` — a tuning field that doesn't belong to the declared `kind` (e.g. `nlist` on a `flat` spec) is a 400 rather than silently dropped, so an operator's typo cannot vanish. An unknown `type` documents as 404; see `iss-vector-index-define-status` in `docs/ISSUES.md` for a postgres-adapter divergence where an unknown type currently falls through to a misleading 400 instead.

## Index builds

Three implementations sit behind the swappable `VectorIndex` trait in `control-plane-core` (pure — no iceberg/arrow/object-store deps), selected at build time via `IndexSpec`:

- **Flat** (#207, the default) — exact brute-force over packed `f32` rows with a parallel identity-key column. Cosine (default) and L2 metrics; the metric is a property of the built index, not a per-query choice.
- **IVF-Flat** (#210, `kind=1`, opt-in) — hand-rolled deterministic k-means (fixed-seed k-means++ init, capped Lloyd iterations) with `nprobe` cluster probing. `nprobe >= nlist` provably equals the exact Flat result — the test oracle.
- **HNSW** (#215, `kind=2`, opt-in) — hand-rolled deterministic Malkov–Yashunin graph (fixed-seed `SplitMix64` level draws, single-threaded insertion, diversity neighbor heuristic). Build knobs `M`/`efConstruction` (defaults 16/200); no exact oracle, so correctness is a recall threshold against Flat. Chosen over Vamana/DiskANN because loom loads the whole blob into memory to search.

All builds are byte-deterministic for a given input row order (build order is fixed), so the serialized blob is reproducible. The build is a primitive plus a `build_vector_index` queue job processed by the worker (via the engine's build RPC): as of covered snapshot `S`, it reads all vectors live at `S` (cold Parquet plus hot inline) through the serving read path, builds the index per the named declaration, writes the Puffin sidecar to the object store, and commits the `vector_index` mirror row plus a lineage event in one transaction — the index is a governed, lineage-tracked artifact riding the snapshot. loom has no REST catalog, so the Postgres mirror row replaces the paper's `statistics-file` snapshot binding; the file format stays a standard Iceberg Puffin sidecar. The build's lineage input node uses the canonical `DatasetRef::from(table)` form, matching the flush/landing/transform emitters (#295). The monolithic build function was decomposed onto named seams (`resolve_build_inputs` / `collect_vectors` / `declared_dim` / `write_sidecar` / `build_lineage_event` / `bind_index_and_emit`), with the `IndexSpec::build` construction match in core (#320); the same slice fixed the hot-delta reader's hardcoded `Int64` identity so String/Integer identity types work end-to-end (#320). Cross-crate test fixtures for the vector/wire clusters live in `//src/testing` (#324).

## The /search endpoint and governance

Engine-side, `vector_search` performs the cold∪hot merge: look up the newest mirror row for `(table, index_name)` with `covered_snapshot S <= Q`, read and decode the Puffin index, run its top-k; then score the inline hot delta — rows born in `(S, Q]` and alive at `Q` — **exactly** (brute-force, same `distance` function), and merge via `merge_topk`. The freshness invariant: approximation applies only to the cold tier; a row landed inline after `S` is counted exactly once and is never dropped by cluster or graph pruning, for any `nprobe`/`efSearch` — and a row flushed between `S` and `Q` is counted once (in the index, excluded from the delta). Hot and cold feed identical `f32` bits to the same distance function, so scores cannot diverge. A query with no bound index is a deterministic `NoIndex` error.

Externally, `POST /search/{type_name}/{index_name}` on query-api (#227) accepts `{query, k}` plus the optional per-query knobs `nprobe` (IVF) and `ef_search` (HNSW), applied via `VectorIndex::apply_query_knobs` to the matching kind only. Column, metric, kind, and dim are resolved server-side from the mirror row; the response is a ranked `{id, distance}` list (ascending, at most `k`) — clients re-hydrate properties through the governed `/objects`. `k` is capped at `K_MAX = 1000`; a query-dim mismatch is a 400 (`DimMismatch`); no built index is a 404; query-api stays zero-DataFusion (a Flight ticket for the kNN, `FlightSqlClient::execute` for the post-filter). Governance is layered: a coarse type-level `Read` gate (deny or unknown type → uniform 403, no existence leak), then a row-filter post-filter — surviving candidate ids are re-checked against the subject's row policy via a governed identity-projection read, so a forbidden row is never returned (the list may be shorter than `k`). A policy that denies or masks the identity column fails closed with a deliberate 403 on both the empty- and non-empty-row-filter paths (#243), since the response values *are* identity values.

## Rebuild and staleness triggers

A flush end-caps live inline rows into a cold Parquet snapshot the index does not cover, so just-flushed vectors would fall out of both k-NN legs until the next build. Auto-rebuild (#240) closes this: `iceberg_flush::flush_table` enqueues one `build_vector_index` job per declared vector index on the flushed table **atomically with the end-cap**, threaded into the catalog's single commit transaction via the `CommitExtras.jobs` seam — a flush that commits can never forget to schedule its repair, and a rolled-back flush enqueues nothing. Dedup is a single atomic insert-if-absent against **pending** (`available`) jobs only: a burst of flushes coalesces to one rebuild-against-latest, while a flush during a *running* build still enqueues a fresh job (the running build fixed its covered snapshot before the flush and cannot cover it). There is deliberately no row-count threshold — the gap is a correctness/visibility gap, not a cost knob — and freshness is restored with bounded staleness (the queued build's latency), the same tradeoff loom accepts for inline external visibility. The trigger covers flush and the governed UPDATE/DELETE replace path: overwrite and truncate commits enqueue the same deduped rebuilds via the `rebuild_jobs_for` helper both paths share (#338) — a pending job enqueued by either path suppresses the other's, and one rebuild at the newer snapshot covers both commits. Compaction is excluded by design (it rewrites already-indexed cold files).

## Known gaps

- `#fut-cow-arrow-native` — Arrow-native COW read leg that lifts the UPDATE/DELETE rejection on vector-bearing types (folds in the rebuild-on-replace fix).
- `#fut-puffin-vector-index-ann` — the deferred remainder: Vamana/DiskANN, clustering, distributed/disaggregated build and query, cold-index ACL pruning, Puffin-sidecar GC, more metrics/element types.
- `#fut-vector-index-drop` — no `drop_vector_index`; declarations can be replaced but not removed, and dropped-index sidecar/mirror GC is unsolved.
- `#fut-vector-json-serving` — per-object JSON reads skip vector properties; embeddings are served via columnar Arrow only.
