# Overwrite Output Mode — Design

**Slice:** Transform pillar. Today every queue-driven transform commits a brand-new
**append** snapshot (`run_transform` always calls `tx.append_files`). This adds a selectable
**output mode** — `Append` (today's behavior, default) or `Overwrite` (replace the output
table's contents) — backed by a new DuckLake-faithful `replace_files` transaction primitive.
Compaction and watermark-incremental output are deliberately deferred (a later slice; both
will reuse the `replace_files` primitive this slice introduces).

## Motivation

A transform that re-derives a table from scratch on each run has no way to *replace* the
output today — it can only append, so each run's rows pile onto the last and the table grows
without bound (and reads see stale + fresh rows mixed). Overwrite makes "re-derive this table"
a first-class operation: the new result becomes the table's entire live contents, while older
snapshots still time-travel to the prior contents.

## The primitive: `Tx::replace_files`

A new staged transaction op alongside `append_files`, on the `ControlPlane` `Tx` trait:

```rust
/// Replace the table's live data files with `files` in this snapshot: the currently-live
/// files are expired at the new snapshot (still visible at older snapshots — time travel
/// preserved), and `files` become the table's live contents. Staged; applied at commit.
async fn replace_files(&mut self, table: &TableRef, files: &[DataFile]) -> Result<()>;
```

Where `append_files` adds `ducklake_data_file` rows (`begin_snapshot = new`, `end_snapshot =
NULL`) and **accumulates** table stats, `replace_files` (in `commit_snapshot`):

1. **Expires the live files**:
   `UPDATE ducklake_data_file SET end_snapshot = $new_snapshot_id
    WHERE table_id = $id AND end_snapshot IS NULL`.
   The expired rows remain in the catalog with a closed `[begin, end)` range, so a read *at an
   older snapshot* still lists them; a read at the new snapshot does not.
2. **Resets the table-level stats**: `ducklake_table_stats.record_count` and
   `file_size_bytes` are recomputed from the new files only (not accumulated onto the prior
   live total). `next_row_id` keeps advancing — row-ids are never reused, so the new files'
   `row_id_start` continues from the current `next_row_id`. `ducklake_table_column_stats` rows
   for the table are cleared so they recompute from the new files.
3. **Writes the new files** via the existing `write_data_file` path (data-file row, per-file
   column stats, table-stats accumulation onto the just-reset zero base).
4. **Emits change segments** `deleted_from_table:<id>,inserted_into_table:<id>` (the recipe's
   documented slot for delete/compaction changes; see `changes_made` grammar §4). The change
   string drives DuckLake's change feed, not scan correctness — scan correctness comes from the
   `begin/end_snapshot` ranges and the stats — so the **e2e read-back through DuckDB is the
   correctness arbiter**.

On a **brand-new** output table, step 1 expires zero files and overwrite degenerates to
create+write. `create_table` stays idempotent (no-op if the table is already live), so an
overwrite transform stages `create_table` + `replace_files` whether or not the table exists.

A given table is **either** appended **or** replaced in one transaction, never both
(`run_transform` stages exactly one per output), so there is no intra-commit ordering conflict
between the append loop and the replace loop.

## Threading it through

### control-plane-core (`src/control-plane/core/src/transaction.rs`)
- Add the `replace_files` method to the `Tx` trait (above). No new domain types — it reuses
  `DataFile`/`ColumnSpec`/`TableRef`.

### postgres adapter
- `PgTx` (`transaction.rs`) gains a `staged_replacements: Vec<(TableRef, Vec<DataFile>)>` field;
  `replace_files` pushes onto it. `commit` triggers `commit_snapshot` when any of
  `staged_tables`/`staged_files`/`staged_replacements` is non-empty.
- `commit_snapshot` (`snapshot.rs`) gains a replacement loop after the create-table loop and
  alongside the append loop: for each `(table, files)` replacement, resolve `table_id`, expire
  live files, reset table + column stats, then run the existing per-file write. The append loop
  is unchanged. Both loops contribute `inserted_into_table` segments; replacements additionally
  contribute a leading `deleted_from_table` segment.
- New committed `.sqlx` entries for the expire/reset queries (regenerated by
  `tools/sqlx-prepare.sh`).

### memory adapter (`src/control-plane/memory/src/transaction.rs`)
- `MemoryTx` gains `replace_files`, mirroring the observable semantics against the in-memory
  catalog model: the table's live file set becomes `files`; prior snapshots retain their file
  sets where the memory model represents per-snapshot history (it is a fake — it implements the
  semantics the contract asserts, no more).

### testkit (`src/control-plane/testkit/src/lib.rs`)
- Extend the snapshot-commit contract: append a file, then `replace_files` with a different
  file, and assert the current snapshot lists **only** the replacement (live count reflects the
  new file, not the sum). Run against both adapters.

### transform service
- `src/services/transform/src/run.rs`: add
  `pub enum OutputMode { Append, Overwrite }` (with `Default = Append`); add
  `pub output_mode: OutputMode` to `TransformRequest`; in `run_transform` step 6, branch
  `match output_mode { Append => tx.append_files(...), Overwrite => tx.replace_files(...) }`.
  Everything else (resolve, SQL, conform, write Parquet) is identical.
- `src/services/transform/src/typed.rs`: thread an `output_mode` parameter through
  `run_typed_transform` into the `TransformRequest` it builds.
- `src/services/transform/src/handler.rs`: both wire payloads (`TransformPayload`,
  `TypedTransformPayload`) get an optional `output_mode` field deserialized to `OutputMode`
  (default `Append` when absent, so existing job payloads are unaffected; `"overwrite"` selects
  Overwrite; an unrecognized value is a deserialization error → `Abandon`, consistent with
  today's malformed-payload handling).

## Scope boundaries (deliberate)

- **Overwrite replaces data, not schema.** An existing output table keeps its schema
  (`create_table` is idempotent). A transform result whose columns differ from an existing
  output table is out of scope — schema evolution on overwrite is a future concern. The typed
  path already enforces that the result conforms to the output type's columns; the physical
  path infers columns and assumes they match the existing table on overwrite.
- **Compaction is deferred** — it reuses `replace_files` but adds read-coalesce-rewrite logic
  and a trigger policy (its own slice).
- **Watermark/stateful incremental is deferred** — storage-layer "incremental" is today's
  append; a stateful watermark-tracked delta mode is a separate feature.

## Error handling

Reuses the existing `TransformError` taxonomy unchanged — a replace fails exactly as an append
does (`ControlPlane`/`Write` → Retry with backoff; deterministic → Abandon). A malformed or
unknown `output_mode` in the wire payload surfaces as a payload deserialization error →
`RetryPolicy::Abandon`, matching today's behavior for malformed payloads.

## Data flow (overwrite)

`run_transform` (`output_mode = Overwrite`) → resolve + register inputs → run SQL → (conform,
typed only) → collect batches → write N Snappy Parquet files under the output dir → **one
atomic Tx**: `create_table` (idempotent) + `replace_files` (expire-live + reset-stats +
write-new) + `emit` lineage → returns the new `SnapshotId`.

## Testing

- **testkit snapshot contract** (both adapters): append then replace ⇒ current snapshot lists
  only the replacement file; stats reflect the new file only.
- **postgres snapshot test** (fixture): after append→replace, the expired file has a non-null
  `end_snapshot` and is still listed at the prior snapshot via `catalog().files(table,
  prior_id)`, while `catalog().files(table, new_id)` lists only the new file; table stats are
  reset (record_count = new file's count, not the sum).
- **transform e2e** (fixture): a transform with `output_mode = overwrite` replaces the output
  table's rows — a DuckDB read-back at the current snapshot returns only the new result; a
  **second** overwrite replaces again; a read at the pre-overwrite snapshot still returns the
  old rows (time travel). An `output_mode = append` run is unchanged (regression).
- **handler/wire unit**: the payload parses `output_mode` — absent → `Append`, `"overwrite"`
  → `Overwrite`, an invalid value → a deserialization error.

## Decisions

- **`replace_files` is a distinct staged op, not a flag on `append_files`** — they have
  different stats semantics (reset vs accumulate) and different change segments; a separate
  staging vector keeps `commit_snapshot` readable and the append path untouched.
- **`next_row_id` is never reset on overwrite** — row-ids must stay unique across snapshots for
  DuckLake correctness; only `record_count`/`file_size_bytes` reset to the live (new-files)
  total.
- **The e2e DuckDB read-back is the correctness arbiter** for the `changes_made` string —
  scan correctness derives from `begin/end_snapshot` ranges + stats, so the test proves the
  catalog is read back correctly rather than asserting an exact change-feed string.
- **`output_mode` defaults to `Append`** in the wire payloads so every existing transform job
  payload keeps working unchanged.
