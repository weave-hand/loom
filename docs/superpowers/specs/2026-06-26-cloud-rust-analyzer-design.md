# Cloud rust-analyzer: hermetic binary + vendored rust-project + per-session graph

**Status:** landed. Layers 1–3 complete — `rust-project` is vendored from the
weave-hand/buck2 fork release `rust-project/v2026.06.26.00`, and
`tools/cloud-session-start.sh` regenerates `rust-project.json` per session.

## Problem

The `rust-analyzer-lsp` Claude plugin must work in cloud sessions (the
implementation routines — `loom-complexity-fix`, `loom-duplication-fix`,
`loom-work-checkout` — edit Rust and benefit from LSP navigation). A cloud
session starts from a fresh snapshot and inherits none of a developer's local
machine state, so three independent things must each be satisfied.

## Background: how RA is wired locally

- The plugin shells out to a bare `rust-analyzer` from `$PATH`.
- RA loads loom's buck2 crate graph from `rust-project.json` at the repo root,
  generated by buck2's `rust-project` integration
  (`rust-project develop root//src/...`).
- `rust-project.json` is **gitignored** — it bakes absolute `buck-out` paths, so
  it is machine-specific and cannot be committed.
- The generated json's `sysroot` already points at loom's **hermetic**
  `//tools:rust-host-toolchain` output (not rustup): `--prefer-rustup-managed-toolchain`
  merely runs `rustc --print sysroot` from `$PATH`, and `tools/env.sh` puts the
  hermetic `rustc` first on `$PATH`. So "rustup-managed" is a misnomer here — with
  env.sh active it resolves to the hermetic toolchain. This is the key fact that
  makes cloud generation trivial (no special toolchain-pointing needed).

## The three layers

### Layer 1 — Plugin enablement (LANDED)

Enablement lived only in the developer's user-global `~/.claude/settings.json`,
which cloud sessions do not read. Added a checked-in `enabledPlugins` block to
`.claude/settings.json`:

```json
"enabledPlugins": { "rust-analyzer-lsp@claude-plugins-official": true }
```

`claude-plugins-official` is the default marketplace, so no
`extraKnownMarketplaces` is required.

### Layer 2 — Hermetic rust-analyzer binary (LANDED)

RA now comes from the pinned buck2 toolchain rather than a host `~/.cargo/bin`
rustup shim (which on this host failed — the `rust-analyzer` component was not
installed, so the shim exited immediately and no LSP server started).

- `toolchains/BUCK` — `rust-analyzer-x86_64-linux` `http_archive`, pinned to the
  same `RUST_NIGHTLY`, `rust-analyzer-preview` component.
- `tools/BUCK` — `//tools:rust-analyzer` wrapper genrule (sets `LD_LIBRARY_PATH`
  to the rustc dist `lib/` for librustc_driver and, critically, for the
  proc-macro server's dlopen of proc-macros built against this toolchain's
  libstd). Mirrors `//tools:rustfmt`.
- `tools/env.sh` — `[rust-analyzer]` added to the `TOOLS` map, so
  `.loom/bin/rust-analyzer` shadows any rustup shim (`.loom/bin` is first on
  PATH). `tools/cloud-session-start.sh` already activates `env.sh`, so cloud
  sessions get the symlink for free.
- `tools/cloud-setup.sh` — `//tools:rust-analyzer` added to the snapshot
  pre-warm so the 9.4 MB dist is baked in, not fetched per session. (Same
  `static.rust-lang.org` host the existing rustc/std/clippy/rustfmt dists already
  fetch, so no proxy work is needed.)

### Layer 3 — `rust-project` vendoring + per-session graph (LANDED)

Two sub-problems:

**(a) `rust-project` is not hermetic.** It was a manual `cargo install` from
buck2 source (`integrations/rust-project`, see DEVELOPING.md). Now vendored as
`//tools:rust-project` from the **weave-hand/buck2** fork (which adds a release
workflow), following the **reindeer `.zst` pattern** rather than the btd tarball
pattern — the fork's release assets are bare per-arch `.zst` binaries.

- `tools/BUCK` — `RUST_PROJECT_VERSION = "v2026.06.26.00"`; per-arch `http_file`
  for `rust-project-<triple>.zst`; per-arch decompress `genrule`
  (`zstd -d -c … > $OUT`) carrying the `uses_xz` host-only label (BuildBuddy
  workers have no `zstd`); `command_alias :rust-project` selecting per cpu
  constraint. The fork's tag is path-style (`rust-project/<version>`), served at a
  literal-slash download URL.
- `tools/env.sh` — `[rust-project]="root//tools:rust-project-x86_64-linux"` in the
  TOOLS map (the concrete genrule, not the command_alias trampoline, per the
  existing reindeer/btd convention), so `.loom/bin/rust-project` shadows any host
  `~/.cargo/bin/rust-project`.
- `tools/cloud-setup.sh` — `//tools:rust-project` added to the snapshot pre-warm.
- **To bump:** cut a new fork release tracking loom's pinned `BUCK2_RELEASE`, then
  update `RUST_PROJECT_VERSION` + the two sha256s.

**(b) Generate `rust-project.json` per session.** Because env.sh puts the
hermetic `rustc` first on PATH, the generation command is identical to local:

```
rust-project develop --prefer-rustup-managed-toolchain root//src/...
```

Wired into `tools/cloud-session-start.sh` **after** env.sh activation. The hook
runs it inside a shell that `eval`s env.sh first (the activation block above only
appends env.sh's exports to the profile, which non-interactive tool shells skip),
so both the vendored `rust-project` and the hermetic `rustc` are on PATH. It is
**backgrounded** via `nohup` (the `buck2 bxl` over `root//src/...` is heavy and
must not delay session start; census routines don't use RA and just let the job
finish in the background) and **non-fatal**. Verified locally: produces a valid
636-crate graph with the hermetic sysroot, and RA serves first-party navigation
off it.

## Known limitations

- **No std source navigation.** The hermetic sysroot
  (`//tools:rust-host-toolchain`) merges std rlibs but not the `rust-src`
  component, so `rust-project.json`'s `sysroot_src` points at a non-existent
  `lib/rustlib/src/rust/library`. Go-to-def *into* std types won't resolve.
  First-party (`//src`) navigation — the actual use case — is unaffected. Fixable
  later by adding the `rust-src` nightly component to the host-toolchain genrule
  if std nav is wanted.

## Out of scope

- macOS/aarch64-only dev boxes (the toolchain is x86_64-linux throughout; add
  aarch64 wrappers if that scope ever widens — the http_file/command_alias
  pattern already accommodates it).
- Making local dev stop using rustup-installed `rust-project` (DEVELOPING.md's
  documented flow still works; this spec only adds the hermetic path).
