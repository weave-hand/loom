## query

- [ ] **Vector-index codec silently corrupts on mixed `VectorKey` int/str rows within one index** `{#iss-vector-index-mixed-key-kind-corrupts-decode area:query status:open from:2026-07-02-pillar-idioms-audit-design pr:- spec:2026-07-03-vector-key-codec-homogeneity-design}`
  `codec.rs::write_keys` derives a single `key_kind` header byte from `keys.first()` only (`0` if the first key is `Int` or `keys` is empty, `1` if `Str`), but the per-key write loop then encodes each key by its own actual variant regardless of that header byte (`Int` → 8-byte `i64` LE, `Str` → 4-byte len + UTF-8 bytes). `read_keys` decodes all `row_count` keys uniformly using the single header `key_kind`. None of `FlatIndex::build`/`IvfFlatIndex::build`/`HnswIndex::build` (via the shared `pack_rows`) validate key-kind homogeneity — only vector length vs. `dim` is checked — so a caller can build an index from `rows: Vec<(VectorKey, Vec<f32>)>` containing both `Int` and `Str` keys, and `build()` returns `Ok`. `serialize()` then writes a length-inconsistent identity block relative to its own header, and `decode(&idx.serialize())` fails to round-trip — either erroring `Backend("vector index decode: truncated")` (identity block ends before `row_count` reads complete, the observed case) or, worse, silently misparsing bytes with no error if the two encodings happen to sum to a compatible length. The doc comment on `flat.rs`'s wire-format block ("All vectors share one key_kind (the identity column's logical type)") documents the intended invariant, but nothing enforces it. Found by the `flat_round_trips`/`ivf_round_trips`/`hnsw_round_trips` proptest properties in `#road-test-property-invariants`'s `vector_index_decode_props.rs` (`src/control-plane/core/tests/`), whose original round-trip generator sampled `Int`/`Str` per row (since narrowed to homogeneous keys) — a call shape every public `build()` signature currently accepts without complaint, so this is a genuine seam defect, not a generator artifact. Minimal shrunk case (identical failure mode across all three index kinds): `dim=1`, `rows=[(Int(0), [0.0]), (Str("\0"), [0.0])]`, `metric=Cosine` — `FlatIndex::build` returns `Ok`, `decode(&idx.serialize())` returns `Err(Backend("vector index decode: truncated"))`. Not reachable from today's production callers (`postgres::build_vector_index` sources keys from one object type's single declared identity column, always homogeneous), so latent rather than active — same posture as the now-fixed `#iss-hnsw-deserialize-bounds`/`#iss-flat-ivf-deserialize-bounds` pair before they were exercised. Fix needs a design decision (reject mixed-kind `rows` in `pack_rows`, fail-loud like the existing dim-mismatch check, vs. extend the wire format to carry a key kind per row) touching all three (de)serializers and the on-disk Puffin blob format — out of scope for the test-only slice that found it (`#road-test-property-invariants` is explicitly additive, no production `src/**.rs` changes).

- [ ] **/search can serve superseded or tombstoned cold hits after an inline-shadow mutation** `{#iss-search-cold-superseded-hits area:query status:open from:2026-07-03-overwrite-vector-rebuild-design pr:- spec:-}`
  After a COW slice-1 inline-shadow UPDATE/DELETE (`#road-cow-inline-shadow`, #331), the cold Puffin index still holds the pre-mutation vector (a stale duplicate hit) or a tombstoned identity; the hot/cold merge adds the new row version but does not *suppress* the superseded cold entry, and the query-api row-filter post-filter drops it only when row filters happen to exist (`handler.rs:607`). Cold-suppression belongs to slice 2's compaction consolidation (`fut-cow-inline-shadow`), whose fold-into-new-base commit is a replace-shaped snapshot routing through the shared `rebuild_jobs_for` seam. Surfaced by the `2026-07-03-overwrite-vector-rebuild-design` investigation.

## deploy

- [ ] **Embedded Postgres archive ships no `libxml2`, so the self-extract boot fails on hosts lacking `libxml2.so.2`** `{#iss-embedded-pg-libxml2 area:deploy status:open from:2026-07-01-embedded-postgres-standalone-design pr:- spec:2026-07-03-embedded-pg-config-hygiene-design}`
  The `loom` standalone binary's self-extract path (`managed_postgres_embed::extract_pg` → `standalone/src/main.rs`) unpacks a bundled Postgres whose `postgres`/`initdb` dynamically link `libxml2.so.2`, but the extracted `lib/` dir does **not** contain `libxml2.so.2` (only `pgxml.so`). `managed_postgres::pg_command` sets the child's `LD_LIBRARY_PATH` to exactly `LOOM_PG_LD_LIBRARY_PATH` (which `main.rs` sets to the extracted lib dir on self-extract), so the loader can't find `libxml2.so.2` from the system either — and on hosts whose system libxml2 carries a newer soname (e.g. Arch, which ships `libxml2.so.16`), there is no `.so.2` to fall back to. `initdb` then fails (`error while loading shared libraries: libxml2.so.2`), so a fresh `loom` can't boot its own Postgres. **Untested:** `composite-e2e`/`composite-error-path` inject an *external* `LOOM_PG_BIN_DIR` (the fixture PG), so the self-extract path this bug lives on is never exercised by CI. Workaround today: `tools/dev-up.sh` detects the load failure and symlinks the newest system `libxml2.so.*` as `libxml2.so.2` into a shim dir prepended to `LOOM_PG_LD_LIBRARY_PATH` (benign "no version information available" loader warnings; Postgres core doesn't use libxml2 unless XML functions are called). **Proper fix:** bundle `libxml2.so.2` inside the embed archive (or statically link it / build Postgres `--without-libxml`) so the self-extract path stands alone, and add a self-extract smoke test that doesn't supply `LOOM_PG_BIN_DIR`. Sibling to `#iss-standalone-composite-error-cascade`.
- [ ] **`Config::from_map` requires `LOOM_PG_BIN_DIR` in embedded mode even for client-only connections** `{#iss-embedded-config-requires-pg-bin-dir area:deploy status:open from:2026-07-02-first-admin-bootstrap-cli-design pr:- spec:2026-07-03-embedded-pg-config-hygiene-design}`
  In embedded mode (`LOOM_PG_MODE=embedded`), `service_runtime::Config::from_map` demands `LOOM_PG_BIN_DIR` (and `LOOM_PG_LD_LIBRARY_PATH`) unconditionally — but a process that only *connects* to an already-running Postgres as a client and never spawns `initdb`/`postgres` (e.g. `loom create-admin`, or any future client-only tool) has no use for the PG binary/lib paths. `tools/dev-up.sh` works around it by passing `LOOM_PG_BIN_DIR`/`LOOM_PG_LD_LIBRARY_PATH` to the `create-admin` invocation purely to satisfy config parsing — surfaced when the first version omitted them and `create-admin` failed at startup with `MissingVar("LOOM_PG_BIN_DIR")` despite only needing the DB socket. Fix: require the PG-binary vars only on the PG-lifecycle-owning (managed) path, not for client-only DB connections — e.g. a lighter config surface for `build_pool` clients, or make those fields optional in embedded mode when no cluster is booted in-process.

- [ ] **Governed UPDATE/DELETE leaves a vector index stale (no auto-rebuild on the replace path)** `{#iss-overwrite-vector-index-staleness area:query status:open from:2026-06-29-vector-index-auto-rebuild-design pr:- spec:2026-07-03-overwrite-vector-rebuild-design}`
  `#road-vector-index-auto-rebuild` (PR #240) closes the index-freshness gap for `iceberg_flush::flush_table`, but the sibling overwrite/replace write path (`overwrite_parquet_snapshot`, reached via `Tx::replace_files` from the governed UPDATE/DELETE copy-on-write in `engine-serving`'s `action_writer`) passes an empty job set and does **not** enqueue a rebuild. After a governed UPDATE/DELETE on a vector-indexed type, the rewritten rows are cold (absent from the Puffin index built at the older `covered_snapshot`) and not inline, so they fall out of k-NN / `/search` until a manual rebuild — the same visibility gap `#road-vector-index-auto-rebuild` closes for flush, now on the replace path. Pre-existing and out of that slice's spec scope (flush only; compaction explicitly deferred), so not a regression. **Blocked-by [[fut-cow-arrow-native]] — currently latent, not reachable:** `ensure_cow_supported` (`query-api/src/action.rs:427`) rejects UPDATE/DELETE on any type with a `vector(N)` column, and a vector-**indexed** type necessarily has one, so the mutation 400s before it reaches `overwrite_parquet_snapshot`. The gap only manifests once [[fut-cow-arrow-native]] lifts that guard. The fix is therefore **folded into [[fut-cow-arrow-native]] as an acceptance criterion** (enqueue `build_vector_index` for each declared index on the replace commit via a `rebuild_jobs_for(table)` helper shared with `iceberg_flush::flush_table`) rather than specced standalone — a standalone fix could not be exercised end-to-end while the guard blocks the path. Tracked under [[fut-puffin-vector-index-ann]]; flagged by that slice's final whole-branch review.

- [ ] **`/search` maps an engine-side identity coercion fault as a caller 400 without an operator log** `{#iss-qa-search-badfiltervalue-classification area:query status:open from:2026-07-02-pillar-idioms-audit-design pr:- spec:2026-07-03-search-fault-classification-design}`
  Found in review of `#road-qa-read-path-consolidation` (PR #310). `vector_search`'s row-filter post-filter feeds the engine's own hit identities back through `identity_in_predicate` → `coerce_filter`; if the serving mirror returns an identity cell that does not coerce to the identity's declared logical type (data corruption / logical-type drift — unreachable with valid data, not caller-forgeable), the resulting `QueryError::BadFilterValue` now maps through the **total** `query_error_response` to a structured 400 with no server-side log, where the pre-#312 partial mapping produced an opaque 500 with a `tracing::error!`. A server-data-integrity fault masquerades as a caller fault and loses its operator signal. Deliberately not "fixed" in #310 (special-casing would re-partialize the one total mapping — the refactor's point). Candidate fix: classify the coercion failure at its source in `vector_search` (wrap as an internal/serving error before it reaches the wire mapping) or log at the mapping when the variant arrives on the search path.
