- [x] **Literal comma inside `in:` operand** `{#iss-literal-comma-in-in area:query status:fixed from:comparison-set-operators pr:#145 spec:2026-06-21-filter-set-operand-comma-escaping-design}`
  Fixed (PR #145): the `in:`/`nin:` set-operator split in `query-api/src/filter.rs` now splits on UNESCAPED commas via the new `split_set_operands` helper and unescapes each operand — `\,`→`,` and `\\`→`\` are the only valid escapes; any other escape or a dangling trailing `\` is a hard error, so every string operand (including one with a literal comma or backslash) is representable and round-trippable. The unescaped empty-operand and missing-operand contracts are unchanged.
- [x] **Multi-file DuckLake LIMIT mis-read** `{#iss-multi-file-limit-misread area:query status:fixed from:cross-cutting pr:#131 spec:2026-06-21-multi-file-limit-guard-design}`
  Fixed (PR #131): the bug was a DuckDB-serving-engine defect — a pushed-down `LIMIT` over a multi-file Parquet scan reconstructed values incorrectly. The original fix emitted a stable `ORDER BY <key>` barrier before the `LIMIT` (compiling to DuckDB's TopN, so the `LIMIT` never reached the corruption site), gated by a `SqlDialect::limit_needs_order_barrier()` knob that only `DuckDbDialect` set. The workaround has since been **removed** along with the DuckDB serving engine: loom now serves exclusively over DataFusion (`DataFusionDialect`), which has no such bug and emits a bare `LIMIT`. The order-barrier code path and the `limit_needs_order_barrier()` knob no longer exist. Upstream DuckDB repro context is tracked in [[fut-multi-file-limit-upstream]].

Pinned by `serving_fault_logging` test with `#[traced_test]`: asserts the opaque body contains no leaked detail and `logs_contain` sees the fault. Drops the standing `TODO(serving-tier)` comment.
- [x] **`HnswIndex::deserialize` trusts the serialized blob's header and adjacency** `{#iss-hnsw-deserialize-bounds area:query status:fixed from:2026-06-28-hnsw-vector-index-design pr:#215,#216 spec:-}`
  `HnswIndex::deserialize` (`control-plane/core/src/vector_index.rs`, the `kind=2` arm shipped by [[road-hnsw-vector-index]]) did not validate the decoded header or graph against the buffer: it called `Vec::with_capacity(row_count * dim)` on the untrusted header product before the per-element byte-availability check, and never checked that each decoded neighbor index was `< row_count` or that the referenced layers existed. A corrupt-but-length-consistent blob therefore triggered a large speculative allocation, or an out-of-range neighbor / absent-layer reference that later panicked inside the `#[expect(clippy::indexing_slicing)]` `row_slice`/`layers[c][lc]` access at search time, rather than returning a `bad(...)` error. Surfaced by the slice-3 final review. Fixed: decode now bounds every untrusted `Vec::with_capacity` against the bytes remaining (new `Cursor::remaining()`; data section via `checked_mul`, per-node neighbor lists, `layers`/`keys`), rejects `entry_point >= row_count` and any `nbr >= row_count`, and enforces graph consistency (a neighbor listed at layer `l` must have height `>= l`; `max_layer` must not exceed the entry point's height) — the inductive invariant that makes every `layers[c][lc]` descent access in-range. Five malformed-blob tests in `tests/vector_index.rs`; an independent adversarial review confirmed no panic/allocation vector remains. The sibling unbounded-allocation pattern in the `FlatIndex`/`IvfFlatIndex` decoders is tracked as [[iss-flat-ivf-deserialize-bounds]].
- [x] **`FlatIndex`/`IvfFlatIndex` `deserialize` size vectors from the untrusted header** `{#iss-flat-ivf-deserialize-bounds area:query status:fixed from:2026-06-28-ivf-vector-index-design pr:#219 spec:-}`
  `FlatIndex::deserialize` and `IvfFlatIndex::deserialize` (`control-plane/core/src/vector_index.rs`) called `Vec::with_capacity(row_count * dim)` (and, for IVF, `nlist * dim`) on the untrusted header product before reading any element — the same speculative-allocation class fixed for HNSW in [[iss-hnsw-deserialize-bounds]], but in the `kind=0`/`kind=1` decoders, which `decode()` routes to. A corrupt-but-self-consistent blob drove a large allocation before the per-element `Cursor` reads failed with `truncated`. Unlike HNSW these impls store no graph adjacency (IVF `assignments` are only used in a `probe.contains` membership test, never as an index; `centroid(c)`/`row(i)` are bounded by the derived `nlist`/`row_count`), so there was no neighbor/entry-point panic vector — the gap was purely the unbounded `with_capacity`. Fixed in #219 (follow-up to the HNSW work in [[iss-hnsw-deserialize-bounds]] / #216): each header product (`row_count*dim`, IVF `nlist*dim`) is now bounded against `Cursor::remaining()` via `checked_mul` before allocating, and the `assignments`/`keys` capacity hints are capped with `.min(remaining)`; oversized-header guard tests cover both decoders. Hardening (blobs are loom-internal output of `write_vector_index`), not an active fault.

- [x] **Role-inheritance cycle check not atomic** `{#iss-acl-role-cycle-atomic area:acl status:fixed from:acl-role-hierarchy pr:#125 spec:2026-06-11-acl-role-hierarchy-design}`
  Fixed (PR #125): `add_role_inheritance` now runs its existence check, recursive-CTE cycle check, and edge insert in one transaction guarded by a transaction-scoped advisory lock (`pg_advisory_xact_lock`, the same pattern as `snapshot.rs`'s catalog lock, on a distinct key). - [x] **Flight `do_get` ticket reads any named path without table-membership check** `{#iss-flight-ticket-path-unchecked area:iceberg status:fixed from:2026-06-22-engine-wire-compaction-flight-design pr:#157,#244 spec:2026-06-29-flight-ticket-membership-check-design}`

- [x] **Hermetic-Postgres fixture boot storm exhausts kernel resources** `{#iss-fixture-boot-contention area:test status:fixed from:postgres-fixture pr:#150 spec:2026-06-22-fixture-boot-throttle-design}`
  Fixed (PR #150): `PgFixture::start` now acquires a slot from a process-global `BootThrottle` before `initdb` and holds it (a `_slot: SlotGuard` field declared last, dropped after the server is killed/reaped) for the cluster's lifetime, so at most `K` clusters are alive at once across all test processes and threads. - [x] **Hermetic-Postgres fixture leaks /dev/shm DSM segments, exhausting the tmpfs** `{#iss-fixture-shm-dsm-leak area:test status:fixed from:postgres-fixture pr:#187 spec:-}`
  Fixed (PR #187): `PgFixture::start` booted postgres with the default `dynamic_shared_memory_type=posix`, which allocates dynamic-shared-memory segments as `/dev/shm/PostgreSQL.*`. Teardown SIGKILLs the server (`Drop` → `self.server.kill()`), so postgres never runs its shutdown cleanup and the segments leak; under the boot throttle's up-to-`K` concurrent clusters (see [[iss-fixture-boot-contention]]) they accumulate across runs and exhaust the host's small (2 GB) `/dev/shm` tmpfs, starving later fixtures — observed as the `iceberg-s3-roundtrip` flake (passes in isolation, fails under the concurrent sweep). The boot arg `-c dynamic_shared_memory_type=mmap` relocates DSM to `$PGDATA/pg_dynshmem/`, inside the per-cluster data tempdir (self-cleans on `Drop`, disk-backed not tmpfs), so the `/dev/shm` footprint is zero regardless of teardown signal or concurrency. Distinct from [[iss-fixture-boot-contention]], which addressed SysV *semaphore* exhaustion. Verified: full `buck2 test //src/...` = 170/0 with 0 residual `/dev/shm/PostgreSQL.*` segments after the whole suite.
