## query


- [ ] **/search can serve superseded or tombstoned cold hits after an inline-shadow mutation** `{#iss-search-cold-superseded-hits area:query status:open from:2026-07-03-overwrite-vector-rebuild-design pr:- spec:-}`
  After a COW slice-1 inline-shadow UPDATE/DELETE (`#road-cow-inline-shadow`, #331), the cold Puffin index still holds the pre-mutation vector (a stale duplicate hit) or a tombstoned identity; the hot/cold merge adds the new row version but does not *suppress* the superseded cold entry, and the query-api row-filter post-filter drops it only when row filters happen to exist (`handler.rs:607`). ## lineage

- [ ] **Governed lineage read leaks denied names via the opaque `payload`** `{#iss-lineage-payload-redaction area:lineage status:open from:2026-07-01-lineage-acl-filtering-design pr:- spec:2026-07-03-lineage-governance-hardening-design}`
  `#road-lineage-acl-filtering` governs the **typed** `inputs`/`outputs` of an event (denied `DatasetRef`s are redacted from `events_for`), but the opaque OpenLineage `payload` JSON is carried **verbatim** and may embed denied dataset names (or other governed identifiers) as free-form text. A subject that can reach an event (it holds the `run_id`) can therefore still read a denied dataset's name out of `payload`, defeating least-disclosure for that field. Fix options: scrub known denied refs from the `payload` JSON, drop `payload` from the governed read entirely, or gate it behind a coarser capability. Related: [[fut-openlineage-validation]] (which would give a typed `payload` schema to scrub against).
- [ ] **Lineage fail-closed recovery misses malformed storage-namespace refs** `{#iss-lineage-storage-namespace-fail-open area:lineage status:open from:2026-07-01-lineage-acl-filtering-design pr:- spec:2026-07-03-lineage-governance-hardening-design}`
  `#road-lineage-acl-filtering`'s `is_readable` recovers the spec's "unresolvable → fail-closed" case from the total bridge by treating an `External` result whose namespace is loom-*logical* (`"loom"`/`"loom:type"`) as denied. But a ref that is **malformed under this deployment's own storage namespace** (`s3://<bucket>`/`file://<root>`) also degrades to `External` in `LineageNaming::resolve`, and is then **default-allowed** rather than fail-closed — so such a ref widens rather than narrows disclosure. Narrow corner today (the internally-emitted graph uses logical refs; a malformed storage ref must be injected), but the fail-closed check should also key on the deployment's `site_namespace`. Ties to [[fut-storage-derived-lineage-emit]] (which would make storage-namespace refs the canonical emitted form, raising the stakes).

## deploy

- [ ] **Embedded Postgres archive ships no `libxml2`, so the self-extract boot fails on hosts lacking `libxml2.so.2`** `{#iss-embedded-pg-libxml2 area:deploy status:open from:2026-07-01-embedded-postgres-standalone-design pr:- spec:2026-07-03-embedded-pg-config-hygiene-design}`
  The `loom` standalone binary's self-extract path (`managed_postgres_embed::extract_pg` → `standalone/src/main.rs`) unpacks a bundled Postgres whose `postgres`/`initdb` dynamically link `libxml2.so.2`, but the extracted `lib/` dir does **not** contain `libxml2.so.2` (only `pgxml.so`). `managed_postgres::pg_command` sets the child's `LD_LIBRARY_PATH` to exactly `LOOM_PG_LD_LIBRARY_PATH` (which `main.rs` sets to the extracted lib dir on self-extract), so the loader can't find `libxml2.so.2` from the system either — and on hosts whose system libxml2 carries a newer soname (e.g. Arch, which ships `libxml2.so.16`), there is no `.so.2` to fall back to. `initdb` then fails (`error while loading shared libraries: libxml2.so.2`), so a fresh `loom` can't boot its own Postgres. **Untested:** `composite-e2e`/`composite-error-path` inject an *external* `LOOM_PG_BIN_DIR` (the fixture PG), so the self-extract path this bug lives on is never exercised by CI. Workaround today: `tools/dev-up.sh` detects the load failure and symlinks the newest system `libxml2.so.*` as `libxml2.so.2` into a shim dir prepended to `LOOM_PG_LD_LIBRARY_PATH` (benign "no version information available" loader warnings; Postgres core doesn't use libxml2 unless XML functions are called). **Proper fix:** bundle `libxml2.so.2` inside the embed archive (or statically link it / build Postgres `--without-libxml`) so the self-extract path stands alone, and add a self-extract smoke test that doesn't supply `LOOM_PG_BIN_DIR`. Sibling to `#iss-standalone-composite-error-cascade`.
- [ ] **`Config::from_map` requires `LOOM_PG_BIN_DIR` in embedded mode even for client-only connections** `{#iss-embedded-config-requires-pg-bin-dir area:deploy status:open from:2026-07-02-first-admin-bootstrap-cli-design pr:- spec:2026-07-03-embedded-pg-config-hygiene-design}`
  In embedded mode (`LOOM_PG_MODE=embedded`), `service_runtime::Config::from_map` demands `LOOM_PG_BIN_DIR` (and `LOOM_PG_LD_LIBRARY_PATH`) unconditionally — but a process that only *connects* to an already-running Postgres as a client and never spawns `initdb`/`postgres` (e.g. `loom create-admin`, or any future client-only tool) has no use for the PG binary/lib paths. `tools/dev-up.sh` works around it by passing `LOOM_PG_BIN_DIR`/`LOOM_PG_LD_LIBRARY_PATH` to the `create-admin` invocation purely to satisfy config parsing — surfaced when the first version omitted them and `create-admin` failed at startup with `MissingVar("LOOM_PG_BIN_DIR")` despite only needing the DB socket. Fix: require the PG-binary vars only on the PG-lifecycle-owning (managed) path, not for client-only DB connections — e.g. a lighter config surface for `build_pool` clients, or make those fields optional in embedded mode when no cluster is booted in-process.

## test


- [ ] **`/search` maps an engine-side identity coercion fault as a caller 400 without an operator log** `{#iss-qa-search-badfiltervalue-classification area:query status:open from:2026-07-02-pillar-idioms-audit-design pr:- spec:2026-07-03-search-fault-classification-design}`
  Found in review of `#road-qa-read-path-consolidation` (PR #310). `vector_search`'s row-filter post-filter feeds the engine's own hit identities back through `identity_in_predicate` → `coerce_filter`; if the serving mirror returns an identity cell that does not coerce to the identity's declared logical type (data corruption / logical-type drift — unreachable with valid data, not caller-forgeable), the resulting `QueryError::BadFilterValue` now maps through the **total** `query_error_response` to a structured 400 with no server-side log, where the pre-#312 partial mapping produced an opaque 500 with a `tracing::error!`. A server-data-integrity fault masquerades as a caller fault and loses its operator signal. Deliberately not "fixed" in #310 (special-casing would re-partialize the one total mapping — the refactor's point). Candidate fix: classify the coercion failure at its source in `vector_search` (wrap as an internal/serving error before it reaches the wire mapping) or log at the mapping when the variant arrives on the search path.
