## ingest

- [ ] **A brand-new table's Iceberg create runs outside the landing transaction, unguarded by the mirror-row race fix** `{#iss-iceberg-create-outside-tx-framing area:ingest status:open from:2026-07-14-stream-first-declare-race-kind-design pr:- spec:-}`
  `ensure_iceberg_table` (`src/control-plane/postgres/src/iceberg_landing.rs:628`, called from the stream Parquet path at `:935`; its create-if-absent body is `:639-648`) runs BEFORE and outside the landing transaction and is never rolled back. Two writers racing to create a brand-new `s.t` — one a batch land, one a stream-declaring land — both call it; whichever runs first creates the Iceberg table, and a stream declarer creates it WITH framing columns (`include_framing=true`). The mirror-row race is now correctly guarded (`ensure_table_witnessed` makes a stream declare that loses the mirror-row create race see the winner's table as pre-existing and get rejected with "cannot convert existing batch table"), but if the losing stream declarer's ICEBERG create won that separate race, the batch winner's table is left backed by a framing-schema'd Iceberg table (three extra reserved columns) whose mirror row says batch. The window exists on `main` today; this branch does not change the create ordering, and pre-fix the outcome was strictly worse (the mirror got converted too), so the branch is a strict improvement, not a regression. Filed rather than fixed here: fixing it means making a non-transactional object-store create participate in a transactional decision, and the competing approaches have different blast radii — reorder the write path so the Iceberg create follows the mirror reconcile (but the Parquet write needs the Iceberg schema first), issue a compensating drop on rejection, or accept the window and reconcile at flush — each needs its own spec and its own test surface.
- [ ] **`land_parquet`'s stream-vs-batch routing probe is a blind pre-transaction read, racing a concurrent first-declare** `{#iss-batch-land-routes-blind-to-concurrent-declare area:ingest status:open from:2026-07-14-stream-first-declare-race-kind-design pr:- spec:-}`
  `land_parquet` (`src/control-plane/postgres/src/iceberg_landing.rs:857-873`) decides stream-vs-batch routing with a read-only probe on a separate pooled connection, taken BEFORE the landing transaction begins: it looks up the live `table_id` and checks `stream.stream_table` for an existing declaration, then routes to `land_parquet_stream` iff that probe sees a declaration or `decl` itself declares one — otherwise it takes the plain BATCH path, `append_parquet_snapshot`, which never calls `reconcile_stream_mode` and never stamps framing/offsets. A plain BATCH land (`decl = StreamDecl::None`) whose probe sees no table thus commits to the batch path before its transaction even opens. If a concurrent stream-declaring land creates and declares that same table and commits first, the batch lander's `ensure_table` inside its own transaction resolves the table-create race to the winner's `table_id` — but by then routing is already decided, so the batch lander appends unframed rows into what is now a declared stream table, producing unframed rows in a stream table or an opaque schema-evolution error (the extra reserved framing columns the winner added). This is the mirror image of the race `#iss-stream-first-declare-race-kind` closed on this branch: that fix serializes the mirror-row *create* and the stream-registry *declare* against each other inside the transaction; this bug is in the *routing decision* made outside and before any transaction, so that fix does not reach it. **Differs from [[iss-iceberg-create-outside-tx-framing]]:** that entry is about the Iceberg **physical schema** (the object-store create, with or without framing columns) being decided outside the transaction; this entry is about the separate **mirror/registry routing decision** — which code path (`land_parquet_stream` vs `append_parquet_snapshot`) a write takes — being made on a stale pre-transaction read of `stream.stream_table`. The two windows can be hit independently. Filed rather than fixed here: the Parquet files for the batch path are written and stats-computed BEFORE the transaction begins, and framing columns must already be present in those files for the stream path to be correct — so a batch lander that only discovers the race once inside its transaction cannot simply switch onto the stream path at that point; it must either fail the write outright or restart the whole land operation from the routing decision (re-probe → take the stream path → rewrite the Parquet WITH framing columns). That is a restructure of `land_parquet`'s attempt/retry shape, it interacts with `ensure_iceberg_table` (itself also running pre-transaction, per [[iss-iceberg-create-outside-tx-framing]]), and it needs its own spec and its own test surface — not a fix folded into this branch.

## transform

- [ ] **Pre-declaration data files are held forever by the MV floor's fail-safe** `{#iss-mv-floor-holds-pre-declaration-files area:transform status:open from:2026-07-12-mv-watermark-aware-gc-design pr:- spec:2026-07-14-mv-floor-unframed-files-design}`
  `declare_stream` (`control-plane/postgres/src/stream.rs`) can be applied to a table that **already has data files** written as a plain batch table; those files carry no `loom_offset` column stat. The MV floor guard is deliberately fail-safe — a file whose `loom_offset` max stat is missing is **held**, never reclaimed — so once any MV registers against such a table, its pre-declaration files become permanently unreclaimable and inflate `GcSummary.held_by_mv_floor` with no laggard MV to blame (the warning names a bucket's slowest MV; these files belong to no bucket). Bounded, visible, and never lossy — but a genuine "GC never converges for this table" case, and a misleading metric. **Fix shape:** distinguish "no `loom_offset` stat because the file predates the stream declaration" from "no stat because stats are missing" — e.g. record the declaring snapshot on `stream.stream_table` and exempt files whose `begin_snapshot` is below it (they were never part of the offset-framed stream, so no MV can want them), or backfill/deny declaration over a table with existing unframed files. Surfaced by `#road-mv-watermark-aware-gc`.
- [ ] **A concurrent CDC declaration and MV registration can still interleave into the wedged state** `{#iss-mv-cdc-declare-register-race area:transform status:open from:2026-07-14-end-cap-mv-floor-seam-design pr:- spec:-}`
  The MV/CDC mutual exclusion shipped in #443 is enforced from **both** sides — `define_transform` refuses a micro-batch MV whose source is a declared CDC table (`pg_refuse_mv_over_cdc_source`), and `reconcile_stream_mode` refuses a CDC declaration on a table a micro-batch MV already sources (`pg_refuse_cdc_over_mv_source`) — which closes the **sequential ordering** hole (register-then-declare, declare-then-register). What remains is the genuine **race**: the two guards run in **separate transactions with no shared lock**, so a `land_cdc` (`?mode=cdc`) committing concurrently with a `define_transform` can have each read a snapshot in which the other's row does not yet exist, both pass, and both commit — leaving exactly the wedged state the guards exist to prevent (a micro-batch MV sourcing a declared CDC table: `mv_delta_scan` reads log sources only, so the MV can never run, its watermark can never advance, and `mv_floor` pins the source at offset `0` forever — permanently declining that table's consolidate fold, which then skips-and-re-arms on every attempt). **Filed rather than fixed, deliberately:** `define_transform` now takes `lock_key(source)` — the per-table key GC/flush/consolidate already serialize under — so the remaining work is for the ingest *declaration* path (`land_cdc` / `reconcile_stream_mode`) to take `lock_key(table)`, the same per-table key `define_transform` now holds, so the two serialize; which changes the **ingest hot path's locking profile** (every `?mode=cdc` write would serialize against transform registration). That is a design decision about ingest throughput vs. structural exclusion, and a human should make it rather than have it fall out of a defect fix. Narrow in practice (it needs a first-ever CDC declaration to land inside one `define_transform`'s transaction) and loud in effect (the MV never runs and the consolidate skip warns, naming the laggard), never silent data loss. The whole exclusion lifts when [[fut-mv-cdc-source]] lands. Related: [[fut-mv-start-at-policy]] (the source-floor bootstrap that shipped `define_transform`'s per-table lock closed the sibling registration race).
- [ ] **An in-flight micro-batch run can re-create watermark rows for a def that no longer exists** `{#iss-mv-watermark-ghost-rows area:transform status:open from:2026-07-12-mv-watermark-aware-gc-design pr:- spec:2026-07-14-mv-watermark-ghost-rows-design}`
  The registration→watermark reconciliation is complete on the **admin** paths: `delete_transform` deletes the MV's `stream.mv_watermark` rows with the def, and `define_transform` deletes the *previous* output's rows when a redefinition moves an MV off it (both certified by a testkit contract on both backends), so no watermark key can outlive every def that names it — a ghost key would sit in `mv_floor`'s reader set and floor its source forever, unreachable by any escape hatch. What remains is the inherently **racy** case: a micro-batch run already in flight whose watermark CAS (`advance_mv_watermark`) commits *after* its def was deleted (or redefined away) re-inserts rows under the now-defless `mv` key, since the CAS neither takes the define lock nor re-checks the registration. The source is then floored at that key's offsets with no def to point the operator at, and the only cure is a manual `delete from stream.mv_watermark`. Bounded in practice (one micro-batch's worth of lag, and the MV is being torn down anyway) but it is the same "GC never converges" shape as [[iss-mv-floor-holds-pre-declaration-files]]. **Fix shape:** make the CAS conditional on the def still naming the key (a `where exists (…)` guard, or take the same advisory lock `define_transform` holds), or sweep watermark keys named by no def as part of GC — either way the reconciliation becomes structural rather than best-effort.

## iceberg

- [ ] **Orphan-sweep `ZERO_GRACE` test is flaky at the grace-window boundary** `{#iss-orphan-sweep-zero-grace-boundary-flake area:iceberg status:open from:2026-07-14-mv-register-source-floor-design pr:- spec:-}`
  `sweep_orphans` (`control-plane/postgres/src/orphan_sweep.rs`) holds a candidate whose object age has not passed the grace window with `if modified_ms >= cutoff_ms` (`:152`), where `cutoff_ms = now_ms - grace` (`:145`), both at millisecond precision. Under the fixture's `ZERO_GRACE` (`tests/orphan_sweep.rs:24`) `cutoff_ms == now_ms`, so a stray object written in the **same millisecond** the sweep captures `now_ms` satisfies `modified_ms >= cutoff_ms` and is **held instead of deleted** — the sweep then deletes 0 objects, not 1, and `sweep_keeps_referenced_puffin` (`:368`) fails on `assert!(!stray.exists())`. Nondeterministic: it fails only when no clock tick lands between the test's write and the sweep's `now_ms` (reproduced locally ~1 run in 3; green on the same code otherwise). All six `ZERO_GRACE` tests share the latent race; `sweep_keeps_referenced_puffin` trips it most because its extra setup (vector-index rows + two object writes) widens the same-millisecond window. **Discovered as CI flake on PR #445** (`affected` pulled `orphan-sweep` in only because that PR's `iceberg_gc.rs` comment edit put the file in btd scope — the PR does not touch `orphan_sweep.rs`; the `>=` is identical on `main`). **Fix shape — needs a human's call, two candidates:** (a) production — the boundary is arguably off-by-one: a file whose age has reached *exactly* `grace` has satisfied the window and could be swept (`modified_ms > cutoff_ms` to hold, i.e. hold only objects strictly younger than the grace age) — but that loosens a write-race safety window and is a semantics decision, not a test tweak; or (b) test-only — age written orphans deterministically (back-date their mtime, or drive the sweep off an injected clock) so the six `ZERO_GRACE` tests stop depending on wall-clock advancing. The production `>=` is harmless in production (grace is a real, minutes-scale window; the exact-millisecond boundary never binds a genuinely-old orphan) — this is a test-determinism defect, not a data-loss one.
